# Capability: Syntax Highlighting

## User Need
As a Trellis author (human or AI agent), I want the wire frame source I read and write in every code editor to be syntax highlighted so that I can tell comments, strings, pointers, parameters, keywords, types and attributes apart at a glance and spot mistakes sooner.

## Product Decisions
* **[2026-11-23] CI-024 Highlighting everywhere (planned):** All Trellis source text in the app is syntax highlighted by one shared highlighter, in every place that shows or edits it: (1) the source tabs of a feature's details page, (2) the source text of the Macros page and (3) the read-only source of every example on the Examples page. The `Add feature` dialog's description is ordinary text, not Trellis source, and is not part of it. Highlighting is purely visual: it does not change what is parsed, compiled, saved or shown in the preview, and the syntax itself does not change.
* **[2026-11-23] CI-024 Token classes (planned):** Each piece of text gets one of these looks, and anything else (spaces, `|`, `,`, `=`, bare attribute values such as `bold` or `lg`, a `#` that is not at column 0) stays plain. (1) Comment: a whole line whose first character is `#`, as in `CI-023 Comments (planned)` in the `trellis-ast` capability; an indented `#` or a `#` after other text is not a comment and is not highlighted as one. (2) String: a double-quoted text, including the quotes (`"Log in"`); a `$name` inside quotes is part of the string and looks like a string. (3) Pointer: `@Entity.Field` with an optional `.label` or `.mock` (`@User.FirstName.label`). (4) Parameter: `$1`, `$name` and a field reference `$item.title`, as in `/capabilities/macros/capability.md`. (5) Keyword: `Def` and `Each`, the two reserved words of the macro syntax. (6) Type: any other word that starts with an upper-case letter, so the core types (`Page`, `Box`, `Text`, `Row`, `BoxRow`, `Spacer`, `Image`, `Table`, `TableColumn`) and macro names alike. (7) Attribute name: a lower-case word, with `-` and dotted fields allowed, directly followed by `=` (`width=`, `link-to=`, `font-size=`, `as=`, `item.title=`). (8) Number: a run of digits (`width=3`, `16:9`). The highlighter does not check meaning: a misspelt type or an unknown attribute is highlighted by its shape and still reported by the parser as before.
* **[2026-11-23] CI-024 Colours (planned):** The classes use clearly different colours that are readable on the app's background in both the light and the dark theme, with comments dimmed and keywords and types the most prominent. Pointers and parameters look different from each other and from strings.
* **[2026-11-23] CI-024 Editing feel (planned):** The editable editors keep what the text areas had: monospace small text, the same card placement and height (the Macros page's editor fills its card, a feature's source tab fills the space under its tabs and keeps its minimum height), the placeholder text when empty, the focus ring, no spell checking, and long lines wrap. Every edit still updates the source immediately and is saved automatically as before, and errors, tabs and the preview behave exactly as before. In addition an editor has undo and redo (`Ctrl+Z`, `Ctrl+Y` or `Ctrl+Shift+Z`), and pressing Enter starts the new line at the indentation of the line above, which helps with the 2-space nesting. `Tab` is not captured: it moves the focus out of the editor, as in a text area. The read-only examples can be selected and copied, take no input, and scroll sideways for long lines as they did.
* **[2026-11-23] CI-024 Accessible names (planned):** Each editor keeps its accessible name: `Page N source` for a feature's source tab, `Macros source` for the Macros page and `<title> source` for an example, so they can still be found by label.
* **[2026-11-23] CI-024 Line numbers (planned):** This amends `CI-024 Editing feel (planned)`. Every code editor (the feature source tabs, the Macros page and the read-only examples) shows a line number gutter at its left, starting at 1 for the first line of the text the editor holds. The numbers match the `Line <n>:` of the error messages, which are counted in that same text (within the selected page's text in a source tab, in the whole text on the Macros page, in the example's own source on the Examples page), so an error can be found by its number. A long line that wraps is numbered once, on its first row. The gutter is a muted, non-selectable column, so selecting and copying text (including a read-only example) never copies the numbers, and it does not change the text, the saved source or the accessible name of the editor. There is no toggle.
* **[2026-11-23] CI-024 Highlighting everywhere:** Implemented as `CI-024 Highlighting everywhere (planned)`: the feature source tabs, the Macros page and the Examples page share one highlighter; the `Add feature` dialog is unchanged.
* **[2026-11-23] CI-024 Token classes:** Implemented as `CI-024 Token classes (planned)`.
* **[2026-11-23] CI-024 Attribute names and values:** This amends `CI-024 Token classes (planned)` and `CI-024 Colours (planned)`. An attribute is highlighted as one purple `attributeName` span: the name, the `=`, and a following bare or numeric value (`id=login`, `width=3`, `font-size=lg`, `aspect-ratio=16:9`, `item.title=`). A quoted or pointer value after `=` keeps its own string or pointer colour. Attribute and number colours are the same purple in both themes.
* **[2026-11-23] CI-024 Colours:** Implemented as `CI-024 Colours (planned)`: comments dimmed, keywords and types bold, pointers and parameters distinct from each other and from strings, in both themes.
* **[2026-11-23] CI-024 Editing feel:** Implemented as `CI-024 Editing feel (planned)` and `CI-024 Line numbers (planned)`.
* **[2026-11-23] CI-024 Accessible names:** Implemented as `CI-024 Accessible names (planned)`.

## Technical Decisions
* **[2026-11-23] CI-024 CodeMirror 6 (planned):** The editors are CodeMirror 6, added with `pnpm add @codemirror/state @codemirror/view @codemirror/language @codemirror/commands` (the individual packages, not the `codemirror` bundle and not `basicSetup`, so the editor has no gutters, folding, autocompletion or search that the text areas did not have). The extensions used are `history`, the default and history keymaps, `drawSelection`, `lineWrapping` (editable only), `EditorState.readOnly` and `EditorView.editable` (read-only only), the language and its highlighter, and the theme.
* **[2026-11-23] CI-024 Language module (planned):** `src/web/syntax/highlight.ts` is a DOM-free module with the language definition. It exports `trellisLanguage`, a `StreamLanguage.define({ token })` (so Trellis does not need a Lezer grammar), and `tokenizeLine(line: string): { text: string; token: string | null }[]`, which runs the same `token` function over a line with `StringStream`, so the tokeniser is testable without a DOM or an editor. The `token` function tries these in order: a comment (`stream.sol()` and the next character is `#`, then the rest of the line, token `comment`); spaces (no token); a string (`^"[^"]*"`, `string`; the syntax has no escapes, so no `\\` case); a pointer (`^@[A-Za-z][\w.]*`, `variableName.special`); a parameter (`^\$(?:1(?![A-Za-z0-9_])|[A-Za-z]\w*(?:\.[A-Za-z]\w*)*)`, `variableName`); a keyword (`^(?:Def|Each)\b`, `keyword`); a type (`^[A-Z][A-Za-z0-9]*`, `typeName`); an attribute name (`^[a-z][\w-]*(?:\.[a-z]\w*)*(?==)`, `attributeName`); a number (`^\d+`, `number`); otherwise one character with no token. This is the tokeniser sketched for the iteration request, with the comment limited to column 0, `$1` and field references added, the keywords reduced to the two that exist and the string pattern matching the syntax's escape-free quotes.
* **[2026-11-23] CI-024 Highlight style (planned):** The token names map to CodeMirror's `tags` and are turned into CSS classes with `tagHighlighter`, exported from `highlight.ts` as `trellisHighlighter`, not with a `HighlightStyle` of fixed colours, so the colours can follow the app's theme. The classes (`tok-comment`, `tok-string`, `tok-pointer`, `tok-parameter`, `tok-keyword`, `tok-type`, `tok-attribute`, `tok-number`) are given colours in `src/web/index.css` for the light theme and for the `.dark` theme (the same mechanism the shadcn colours use).
* **[2026-11-23] CI-024 CodeEditor component (planned):** One shared React component, `CodeEditor` in `src/web/components/code-editor.tsx` (it is not a shadcn component, so it is not in `components/ui`), with the props `value: string`, `onChange?: (value: string) => void`, `readOnly?: boolean`, `ariaLabel: string`, `placeholder?: string` and `className?: string`. It is controlled like the `Textarea` it replaces: it creates one `EditorView` on mount and destroys it on unmount, and an effect replaces the document with a transaction when `value` differs from it; `onChange` is called only for edits made in the editor (not for the change that the effect itself makes), so it cannot loop. The latest `onChange` is read through a ref so the view is not recreated on each render. The accessible name is set on the editable element with `EditorView.contentAttributes` (`aria-label`, and `spellcheck=false`), and the placeholder uses CodeMirror's `placeholder` extension. The theme is an `EditorView.theme` that uses the app's CSS variables (transparent background, `font-mono text-xs` equivalent, the `Textarea` border, radius and focus ring) so it matches the cards, and `className` sizes it (`min-h-0 flex-1` for the Macros page, a minimum height for a source tab).
* **[2026-11-23] CI-024 Static markup (planned):** The project's component tests use `renderToStaticMarkup`, which does not run effects and so never creates the editor. The component therefore renders its container with the `ariaLabel` as its accessible name and, in that first render, the value as plain text inside it (replaced by the editor when it mounts), so the tests can still check which text an editor holds and that it is there. The tests that read a `textarea` today (`wireframe-editor.test.tsx`, `macro-editor.test.tsx`, `examples.test.tsx`) read this container instead; typing, undo and selection are not DOM-tested, as for the text areas, and are checked in a browser.
* **[2026-11-23] CI-024 Where it is used (planned):** `WireframeEditor` (`src/web/viewer/wireframe-editor.tsx`) replaces its `Textarea` with `CodeEditor` (`value={pages[current]}`, `onChange` building the joined source as now, `ariaLabel` `Page N source`, the `Page "Page 1" id=page-1` placeholder); `MacroEditor` (`src/web/macros/macro-editor.tsx`) replaces its `Textarea` with `CodeEditor` (`ariaLabel` `Macros source`, its existing placeholder); `ExampleSection` (`src/web/pages/examples.tsx`) replaces its `pre` with a read-only `CodeEditor` (`<title> source`). The `Textarea` component stays for the `Add feature` dialog. Props, state and behaviour of the three components are otherwise unchanged. The editors' keyed remounting follows what they do now: a source tab's editor is keyed by its page position so that switching tabs shows that page's text, with the undo history of the previous tab not carried over.
* **[2026-11-23] CI-024 Line numbers implementation (planned):** This amends `CI-024 CodeMirror 6 (planned)`, which listed no gutters: the line number gutter is the `lineNumbers()` extension of `@codemirror/view` (no new package), added to every `CodeEditor`, and nothing else from the gutter family (no active-line highlight, folding or breakpoints). It is a gutter, not text, so it is outside the document: `value`, `onChange`, selection and copy are unaffected. It is styled in the editor theme (muted foreground colour, no background, a thin border on its right, `font-mono text-xs` like the text, `user-select: none`) with the app's CSS variables so it follows the light and dark themes. In the static markup (see `CI-024 Static markup (planned)`) the first render has no gutter (it exists only once the editor is mounted), so the tests do not check the numbers; they are checked in a browser.
* **[2026-11-23] CI-024 CodeMirror 6:** Implemented as `CI-024 CodeMirror 6 (planned)` and `CI-024 Line numbers implementation (planned)`, with two amendments: `@lezer/highlight` is a direct dependency because `tagHighlighter` and `tags` are imported from it, and `Tab` / `Shift-Tab` are filtered out of the default and history keymaps so Tab moves focus as in a text area.
* **[2026-11-23] CI-024 Language module:** Implemented as `CI-024 Language module (planned)`, with two amendments: the attribute rule consumes the `=` and a following bare word or number (`^[a-z][\w-]*(?:\.[a-z]\w*)*=(?:[A-Za-z][\w-]*|\d+(?::\d+)?)?`) so names and values share one token; leftover unquoted words are still consumed whole so their digits are not taken as numbers.
* **[2026-11-23] CI-024 Highlight style:** Implemented as `CI-024 Highlight style (planned)`.
* **[2026-11-23] CI-024 CodeEditor component:** Implemented as `CI-024 CodeEditor component (planned)`.
* **[2026-11-23] CI-024 Static markup:** Implemented as `CI-024 Static markup (planned)`, with `data-placeholder` and `data-readonly` on the container so the static tests can still see the placeholder and a read-only editor.
* **[2026-11-23] CI-024 Where it is used:** Implemented as `CI-024 Where it is used (planned)`.
* **[2026-11-23] CI-024 Line numbers implementation:** Implemented as `CI-024 Line numbers implementation (planned)`.

## Data Dictionary
- `trellisLanguage`: The CodeMirror `StreamLanguage` for the wire frame source (the core syntax, comments, macros, `Each` and pointers), UI-only and never stored.
- `tokenizeLine(line)`: Splits one line of source into `{ text, token }` pieces, where `token` is one of `comment`, `string`, `variableName.special` (pointer), `variableName` (parameter), `keyword`, `typeName`, `attributeName` (the `name=value` span), `number` or `null` (plain).
- `trellisHighlighter`: Maps those tokens to the CSS classes `tok-comment`, `tok-string`, `tok-pointer`, `tok-parameter`, `tok-keyword`, `tok-type`, `tok-attribute` and `tok-number`.
- `CodeEditor`: The shared highlighted editor component (`value`, `onChange`, `readOnly`, `ariaLabel`, `placeholder`, `className`), controlled by its `value`.
