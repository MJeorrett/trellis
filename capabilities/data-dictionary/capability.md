# Capability: Data Dictionary

## User Need
As a Trellis user, I want to list the entities and fields of my product's data, with their types, so that I can describe the data the features work with next to their wire frames.

## Product Decisions
* **[2026-11-23] CI-016 Data dictionary pane (planned):** The feature details page gets a new pane, the data dictionary, at the bottom of the page. It spans the full width of the page and sits below the wire frame source and wire frame cards (see the `features` capability for the layout). It has a `Data dictionary` heading and a table, one row per field, in the order the rows were added.
* **[2026-11-23] CI-016 Columns (planned):** The table has three columns, in this order: `Entity`, `Field` and `DataType`. `Entity` and `Field` are text inputs whose value is Pascal case. `DataType` is a pick list with exactly four options, in this order: `int`, `bool`, `datetime` and `string`. No other column exists for now (no description, required flag, length, relations or ordering).
* **[2026-11-23] CI-016 Pascal case (planned):** A Pascal case value starts with an upper-case letter A to Z, followed by letters and digits only (`Customer`, `OrderLine2`; not `customer`, `order_line`, `Order Line`, `2Order`). A blank `Entity` or `Field` shows `Entity is required` or `Field is required`, and a value that is not Pascal case shows `Entity must be Pascal case` or `Field must be Pascal case`, in both cases as an inline message under the cell, with the input marked invalid. What was typed is kept exactly (nothing is converted, trimmed or blocked) and is saved like any other edit, so a row can be incomplete while it is being typed. Duplicate rows (the same entity and field twice) are not checked.
* **[2026-11-23] CI-016 Editing (planned):** An `Add field` button under the table adds a row at the end with an empty `Entity`, an empty `Field` and the `DataType` `string`. Each row has a delete button that removes that row. With no rows the table shows an empty-state message (`No fields yet`) instead of the rows, and the `Add field` button is always shown. Every change (typing, picking a type, adding or deleting a row) is saved automatically, with no save button, like the wire frame source. Reordering rows is not part of this iteration.
* **[2026-11-23] CI-016 Global data (planned):** The data dictionary is one list for the whole product, not one per feature: every feature's details page shows the same rows, and a change made on one feature's page is there on all the others and after navigating away and back. It is not connected to the wire frames, the AST or the features list.

* **[2026-11-23] CI-016 Fixed-height pane (planned):** This amends `CI-016 Data dictionary pane (planned)` and `CI-016 Editing (planned)`. The pane has a fixed height: the `Data dictionary` heading, the table's column headers and room for exactly 5 rows, then the `Add field` button. The pane is always that height, so it does not grow or shrink as rows are added or deleted (with fewer than 5 rows the rest of the space is empty, and `No fields yet` is shown in it when there are none). With more than 5 rows the rows scroll vertically inside the pane, while the heading, the column headers and the `Add field` button stay visible. A row's height is fixed, so a row showing an inline message (see `CI-016 Pascal case (planned)`) is taller than the others and simply scrolls like the rest. The pane never makes the page scroll. How the pane fits in the page is in the `features` capability (`CI-016 Static details layout (planned)`).
* **[2026-11-23] CI-016 Data dictionary pane implementation:** The `(planned)` Data dictionary pane, Columns, Pascal case, Editing, Global data and Fixed-height pane decisions are confirmed as implemented, with these clarifications. (1) A value that is only whitespace counts as blank (`Entity is required` / `Field is required`), not as not Pascal case; a value with leading or trailing spaces that is otherwise valid is not Pascal case. (2) The delete button shows a trash icon (the label is only in its `aria-label`, `Delete row N`). (3) The column headers are `Entity`, `Field` and `DataType` plus a fourth, visually hidden `Actions` header for the delete column. (4) The pane has no border of its own beyond a thin ring around the scrolling table; `Add field` is an outline button under it.
* **[2026-11-23] CI-018 Label and MockValue columns (planned):** This amends `CI-016 Columns (planned)`, which said no other column exists. The table gets two more columns after `DataType`, in this order: `Label` and `MockValue`, so the columns are `Entity`, `Field`, `DataType`, `Label`, `MockValue` (then the visually hidden `Actions` column). `Label` is the human-readable text for the field (for example the caption shown next to it in a wire frame) and `MockValue` is a sample value for the field.
* **[2026-11-23] CI-018 Free text (planned):** `Label` and `MockValue` are plain text inputs that accept any text, including blank: there is no Pascal case rule, no required check, no inline message and no check of `MockValue` against the row's `DataType`. What was typed is kept exactly (nothing is converted, trimmed or blocked) and is saved like any other edit. A new row (`Add field`) has an empty `Label` and an empty `MockValue`. Rows saved before this iteration load with an empty `Label` and an empty `MockValue`. The pane's fixed height, row height, scrolling and the focus on the new row's `Entity` input are unchanged; the pane is already the full page width, so the extra columns share it.
* **[2026-11-23] CI-018 Still not connected (planned):** `Label` and `MockValue` are only stored in the data dictionary. They are not used by the wire frames, the AST or the features list (as before, see `CI-016 Global data (planned)`).
* **[2026-11-23] CI-018 Label and MockValue implementation:** The `(planned)` `CI-018 Label and MockValue columns`, `CI-018 Free text` and `CI-018 Still not connected` decisions are confirmed as implemented, unchanged. The empty-state message `No fields yet` now spans all six columns.

## Technical Decisions
* **[2026-11-23] CI-016 Schema (planned):** The row is defined with Zod in `src/web/data-dictionary/schema.ts`: `DATA_TYPES = ["int", "bool", "datetime", "string"] as const`, `DataTypeSchema = z.enum(DATA_TYPES)` and `DataDictionaryRowSchema = z.strictObject({ entity: z.string(), field: z.string(), dataType: DataTypeSchema })`, with the types derived through `z.infer`. The stored rows allow any string in `entity` and `field` (an incomplete row can be saved, see `CI-016 Pascal case (planned)`); the rule itself is the exported `PASCAL_CASE_PATTERN` (`/^[A-Z][A-Za-z0-9]*$/`).
* **[2026-11-23] CI-016 Validation and logic (planned):** The DOM-free logic lives in `src/web/data-dictionary/logic.ts` so it is testable without a DOM: `validateRowField(label: "Entity" | "Field", value): string | undefined` (the inline message or `undefined`), `newRow(): DataDictionaryRow`, `updateRow(rows, index, change)` and `removeRow(rows, index)`, all pure and returning new arrays.
* **[2026-11-23] CI-016 Mock API (planned):** As for the features there is no backend yet. `src/web/data-dictionary/api.ts` exports `getDataDictionary(): Promise<DataDictionaryRow[]>` and `saveDataDictionary(rows): Promise<DataDictionaryRow[]>` (validates with `z.array(DataDictionaryRowSchema)` and rejects with an `Error` carrying the messages), plus `resetMockDataDictionary()` and a `setMockDelay(ms)` for tests. The rows are kept in local storage under the key `trellis.data-dictionary` (exported as `DATA_DICTIONARY_STORAGE_KEY`, JSON text of a `DataDictionaryRow[]`), read and validated on every call. A missing or invalid value is treated as an empty list (there is no seed), and nothing is written until the first save. The storage fallback to an in-memory object when `localStorage` is unavailable follows the one in `src/web/features/api.ts`; if the storage helpers can be shared without changing that file's behaviour they are moved to a shared module, otherwise they are duplicated.
* **[2026-11-23] CI-016 Component (planned):** The pane is a `DataDictionaryPane` component (`src/web/data-dictionary/data-dictionary-pane.tsx`, props `rows` and `onRowsChange`), controlled like `WireframeEditor`. The details page (`src/web/pages/feature-details.tsx`) loads the rows once on mount with `getDataDictionary()`, updates its state immediately on every change and calls `saveDataDictionary` without waiting (a rejection is ignored), as it does for the wire frame; until the rows have loaded the pane shows nothing. The table uses a plain `table` element with the existing shadcn `input` and `button` components and a native `select` for `DataType` (no new shadcn component is added), and every control has an `aria-label` naming its row (`Row 1 entity`, `Row 1 field`, `Row 1 data type`, `Delete row 1`). The pane has no knowledge of the feature, so it can be shown anywhere.
* **[2026-11-23] CI-016 Scrolling rows (planned):** This extends `CI-016 Component (planned)` for `CI-016 Fixed-height pane (planned)`. `DataDictionaryPane` is a flex column with a fixed height (no `flex-1`, so it keeps its size when the page is laid out): the heading, a scroll area, and the `Add field` button. The scroll area is the only part that scrolls (`overflow-y-auto`), has the height of the column header row plus 5 data rows, uses a sticky `thead` so the column headers stay visible, and each data row has a fixed minimum height from a constant (`ROW_HEIGHT`, with `VISIBLE_ROWS = 5`, both exported from the component file) so the 5-row height is computed from them rather than guessed. The pane takes `className` so the page can place it.
* **[2026-11-23] CI-016 Data dictionary implementation:** The `(planned)` Schema, Validation and logic, Mock API, Component and Scrolling rows decisions are confirmed as implemented, with these clarifications. (1) The storage helpers of `src/web/features/api.ts` (the `Pick<Storage, ...>` type, the in-memory fallback and `storage()`) were moved unchanged to `src/web/lib/storage.ts` and are imported by both mock APIs, so the features API behaves as before; both APIs share the one in-memory fallback object, which is harmless because they use different keys. (2) `saveDataDictionary` resolves with the validated rows and, like the features API, waits the simulated delay (400 ms, `setMockDelay(0)` in tests, restored by `resetMockDataDictionary()`). (3) `data-dictionary-pane.tsx` also exports `HEADER_HEIGHT` (36 px) and `SCROLL_AREA_HEIGHT` (`HEADER_HEIGHT + VISIBLE_ROWS * ROW_HEIGHT`, with `ROW_HEIGHT` 48 px); the scroll area has that height as an inline style, and each data row has it as `height` (a table row grows to fit an inline message). (4) The `DataType` select maps the picked value back through `DataTypeSchema.parse`. (5) `updateRow` takes a `Partial<DataDictionaryRow>`; `removeRow` with an index that does not exist returns an unchanged copy. (6) The details page (`FeatureDetailsLoader`) loads the rows in its own effect, separate from the feature, and `FeatureDetailsView` takes them as the optional props `dataDictionary` (the pane is not shown while it is `undefined`) and `onDataDictionaryChange`. (7) Tests: `schema.test.ts`, `logic.test.ts`, `api.test.ts`, `data-dictionary-pane.test.tsx` (all `renderToStaticMarkup`; typing, picking, adding and deleting are not DOM-tested, only the pure logic behind them) and the details view checks in `src/web/pages/features.test.tsx`.
* **[2026-11-23] CI-016 Compact rows:** This amends `CI-016 Data dictionary implementation` (3) to make the table use less vertical space. The inputs, the `DataType` select and the delete button are 28 px high (`h-7`, `icon-sm`) instead of 32 px, the cell padding is `py-0.5`, `ROW_HEIGHT` is 36 px (was 48) and `HEADER_HEIGHT` is 28 px (was 36), so the 5-row scroll area is 208 px high (was 276). Everything else about the pane is unchanged; the details page gives the extra 36 px to the pane, so the wire frame cards are that much shorter.
* **[2026-11-23] CI-016 Focus new row implementation:** `DataDictionaryPane` remembers the position of the row it just added in a ref and, in an effect that runs when `rows` changes, focuses the `input[aria-label="Row N entity"]` of that row inside the pane (the row only exists after the parent has re-rendered). Effects do not run in `renderToStaticMarkup`, so this is not covered by the tests.
* **[2026-11-23] CI-018 Schema (planned):** This extends `CI-016 Schema (planned)`. `DataDictionaryRowSchema` gets `label: z.string().default("")` and `mockValue: z.string().default("")`, still a `z.strictObject`, so a stored row without them is read with empty strings while an unknown key is still rejected. `DataDictionaryRow` is the `z.infer` output type, so `label` and `mockValue` are always `string` in code. `newRow()` returns empty `label` and `mockValue`. The local storage key and the shape of the JSON are otherwise unchanged and no migration is written: old rows are filled in by the schema defaults on read, and the new fields are written on the next save.
* **[2026-11-23] CI-018 Component (planned):** This extends `CI-016 Component (planned)`. `DataDictionaryPane` shows the `Label` and `MockValue` headers after `DataType`, and each row gets two `Input` components with the `aria-label`s `Row N label` and `Row N mock value`, changing the row through `updateRow` like `entity` and `field`. They are not validated, so they never show an inline message or `aria-invalid`. `ROW_HEIGHT`, `HEADER_HEIGHT` and `VISIBLE_ROWS` do not change.
* **[2026-11-23] CI-018 Label and MockValue implementation:** The `(planned)` `CI-018 Schema` and `CI-018 Component` decisions are confirmed as implemented, with these clarifications. (1) `src/web/data-dictionary/api.ts` needed no change: `readRows` and `saveDataDictionary` already parse with `z.array(DataDictionaryRowSchema)`, so the schema defaults fill in old rows on read. (2) The `Label` and `MockValue` columns have no fixed width, so with `table-fixed` they share the remaining width with `Entity` and `Field`. (3) Tests: the new cases are in `schema.test.ts`, `logic.test.ts`, `api.test.ts` and `data-dictionary-pane.test.tsx`; the pane test asserts `aria-invalid="true"` is absent, not the bare word `aria-invalid`, because the shared `Input` component's class list contains `aria-invalid:` utility classes.

## Data Dictionary
- `DataDictionaryRow`: One field of the data dictionary: `entity`, `field`, `dataType`, `label` and `mockValue`. Stored as a JSON list in local storage by the mock API, shared by all features.
- `DataDictionaryRow.entity`: The name of the entity the field belongs to (string, Pascal case; may be `""` or invalid while the row is being typed).
- `DataDictionaryRow.field`: The name of the field (string, Pascal case; may be `""` or invalid while the row is being typed).
- `DataDictionaryRow.dataType`: The type of the field, one of `int`, `bool`, `datetime` or `string` (`string` for a new row).
- `DataDictionaryRow.label`: The human-readable text for the field (string, free text; `""` for a new row and for rows saved before `CI-018`).
- `DataDictionaryRow.mockValue`: A sample value for the field (string, free text, not checked against `dataType`; `""` for a new row and for rows saved before `CI-018`).
