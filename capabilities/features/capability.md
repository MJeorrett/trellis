# Capability: Features

## User Need
As a Trellis user, I want to keep a list of the features of my product and add new ones so that I can see and manage what is being built.

## Product Decisions
* **[2026-11-21] CI-007 Features list (planned):** A features page shows the list of features, one entry per feature, showing its name and description (when it has one), in the order the API returns them (oldest first). While the list is loading the page shows a loading message; when there are no features it shows an empty state that points at the create button; if loading fails it shows the error message. The page has a `Create feature` button above the list.
* **[2026-11-21] CI-007 Create feature (planned):** `Create feature` opens a modal dialog with a `Name` field (required) and a `Description` field (optional, multi-line), a `Create` button and a `Cancel` button. A blank name (empty or only whitespace) is rejected with an inline message and nothing is created. The name and description are trimmed. On success the modal closes, the new feature appears at the end of the list and a success toast is shown; if the API fails the modal stays open with the error shown and the entered values kept. `Cancel`, the close button and Escape close the modal and discard the entered values. While a create is in progress the `Create` button is disabled.
* **[2026-11-21] CI-007 Scope (planned):** This iteration only lists and creates features. Editing, deleting, status, ordering and search are not part of it. Features are not connected to the wire frame viewer or the AST.
* **[2026-11-21] CI-007 Mock API (planned):** There is no backend yet: the features data comes from a mock API that behaves like an async backend (slight delay, may fail validation) so that the UI is written against the same shape a real API will have. Data lives in memory only, so it resets to a few seeded features when the page is reloaded. A real API can replace the mock later without changing the page.
* **[2026-11-21] CI-007 Routes (planned):** The app now has routes: `/features` is the features page, `/wireframe-demo` is the existing wire frame demo (moved unchanged, see the `wire-frame-viewer` capability) and `/` redirects to `/features`. An unknown path redirects to `/features` as well. The features list and the create-feature modal live only on `/features`, never on the wire frame demo route.
* **[2026-11-21] CI-007 No list states (planned):** This amends `CI-007 Features list (planned)`: the features page has no loading state, no empty state and no load-error state for now. It shows the features once the mock API has returned them (nothing in the meantime, and nothing if there are none), and a failed load is not handled specially. The `Create feature` button is always shown. The mock API keeps its simulated delay (see `CI-007 Mock API (planned)`). The create modal is unchanged, including its blank-name message and the disabled `Create` button while a create is in progress.
* **[2026-11-21] CI-007 Features implementation:** The `(planned)` Features list, Create feature, Scope, Mock API, Routes and No list states decisions are confirmed as implemented, with these clarifications. (1) The success toast reads `Feature "<name>" created`. (2) A blank name shows `Name is required` inline in the modal (the first schema message), and the name input is marked invalid while any error is shown. (3) Pressing Enter in the name field submits the form like `Create`. (4) A description of `""` shows only the name in the list. (5) The seed is three features (the last has no description) and the simulated delay is 400 ms.
* **[2026-11-21] CI-007 Top nav:** A top navigation bar is shown on every page with two items: `Features` (`/features`) and `Wireframe` (`/wireframe-demo`). The item for the current page is highlighted. This extends `CI-007 Routes (planned)`; the features list and modal still live only on `/features`.
* **[2026-11-21] CI-008 Feature details page (planned):** Each feature has a details page at `/features/:id`. It shows the feature's name as the page heading (with a link back to `/features`) and, below it, the wire frame editor and preview that the wire frame demo page shows today (the source editor with inline parse errors, and the page tabs preview, with the same behaviour as before: pages, links, toasts). The feature's description is shown under the name when it has one. The features list links each feature's name to its details page.
* **[2026-11-21] CI-008 Wire frame per feature (planned):** Every feature has its own wire frame source, shown in the editor of its details page. A newly created feature starts with a blank source (the blank page, `Page 1`). The three seeded features each have a different sample source, the first being the Login Form sample that the demo showed (see Technical Decisions for where they live). Edits to the source are saved automatically to the mock API (in memory), so they are still there when the user navigates away and back, and are lost when the page is reloaded like all other mock data. There is no save button.
* **[2026-11-21] CI-008 Unknown feature (planned):** `/features/:id` for an id that no feature has shows the message `Feature not found` with a link back to `/features`. As with the list (see `CI-007 No list states (planned)`), there is no loading state: the page shows nothing until the mock API has answered.

The wire frame demo page is removed, along with its `/wireframe-demo` route and its `Wireframe` nav item (the wire frame viewer now lives only on the feature details page, see the `wire-frame-viewer` capability). The top nav has a single item, `Features`, highlighted on `/features` and on every `/features/:id` page.

* **[2026-11-22] CI-014 Code pane per page (planned):** On the details page, the "Wire frame source" card no longer holds one big text area for the whole source: it holds one code pane per page of the wire frame, stacked in source order, followed by an `+ Add Page` button centred under them (as sketched on the `Feature detail` page of the `Features list` wire frame). The "Wire frame" card (page tabs and preview) is unchanged, and so is the side-by-side layout of the two cards. A feature's wire frame is still one source text: the panes are an editing view of that text, so every edit in any pane updates the source immediately and is saved as before (see `CI-008 Wire frame per feature (planned)`), with no save button.
* **[2026-11-22] CI-014 Page pane (planned):** Each pane is a bordered box with a header row `Page:` `<title field>` `Id:` `<id field>`, and below it a monospace text area holding the page's content, i.e. the lines under that page's `Page` line, written exactly as in the full source (the page's children at 2 spaces of indentation). The `Page "..." id=...` line itself is not shown in the text area: it is built from the two fields, `Page "<title>"` followed by ` id=<id>` only when the id field is not empty. A source with several pages therefore gives several panes; the blank source gives one pane with empty title and id and an empty text area (the preview labels it `Page 1`, as before). Lines before the first `Page` line, if a source has any, stay in the first pane's text area so no text is lost. There is no migration: every seeded sample already splits into panes without changes.
* **[2026-11-22] CI-014 Add page (planned):** `+ Add Page` appends a new page after the last one, with the title `Page N` and the id `page-N` (N is its 1-based position) and an empty text area, and the preview gets a new tab for it. It does not move the selected tab. If the id `page-N` is already used by another page the new page gets the next free `page-N`, so adding a page never creates a duplicate id. Removing and reordering pages are not part of this iteration.
* **[2026-11-22] CI-014 Syntax errors per pane (planned):** The parser is still run on the whole joined source and still reports one fail-fast error, but it is now shown under the pane of the page it belongs to instead of under all the panes. For an error inside a page's content, the message keeps its text and its `Line <n>:` prefix counts within that pane (line 1 is the first line of its text area). An error on the page's own line (a title that cannot be written, such as one containing a straight quote `"`, or a `Duplicate page id "<id>"` on the second page) is shown under that pane's header, as the message without a line number. The preview still shows `Fix the source to see the wire frame.` while there is an error.
* **[2026-11-22] CI-014 Features list wire frame, per-page panes:** The `Feature detail` page of the seeded `Features list` wire frame (`src/features/wireframes/features-list.ts`) is updated to sketch this change: its "Wire frame source" pane now holds one bordered box per page (a `BoxRow` with `Page:`, the title box, `Id:` and the id box, then the page's source lines as `Text` lines, for `Log in`/`login` and `Forgot password`/`forgot`) and a last box with a centred `+ Add Page` button (`Spacer`, `Box "+ Add Page"`, `Spacer` in a `Row`), exactly as in the wireframe given for this iteration. The "Wire frame" pane is unchanged, and the other two pages (`Features`, `Create feature`) and their links are unchanged. This amends `[2026-11-22] Features list wire frame, richer example`, whose single list of source lines is replaced.
* **[2026-11-22] CI-014 Implicit page root (planned):** This amends `CI-014 Page pane (planned)` and `CI-014 Syntax errors per pane (planned)`. A pane's text area never contains a `Page` line: the page is created implicitly, once, as the root of each pane, from the title field and the optional id field (an empty id means the page has no `id`, so it cannot be linked to). The text area holds the page's nodes starting at column 0 (`Box` at the left edge, its children indented by 2 spaces), not at the 2 spaces of indentation they have in the full source; the editor adds and removes that indentation itself, so it is never visible or editable. A pane has no way to add another page: typing a `Page` line in a text area is a syntax error shown under that pane, on that line, with the message `Page cannot be written here, it is created from the title and id`, and it never starts a new pane. The only way to add a page is `+ Add Page`. This replaces the "written exactly as in the full source (children at 2 spaces of indentation)" and "lines before the first `Page` line" parts of `CI-014 Page pane (planned)` (stray lines before the first page of a stored source still stay in the first pane, with no migration).
* **[2026-11-22] CI-014 Features list wire frame, pane lines at column 0:** This amends `CI-014 Features list wire frame, per-page panes`: since a pane shows its page's nodes from column 0 (see `CI-014 Implicit page root (planned)`), the source lines sketched in the `Log in` and `Forgot password` boxes of the `Feature detail` page start at column 0 (`Box`, then `  Text “Log in” font=bold font-size=lg`, and so on), so the sketch shows what a pane really contains. Otherwise the sketch is as given for this iteration. The wireframe supplied with the iteration request showed these lines with the page's 2 spaces of indentation still in front; the sketch deliberately differs from it only in that.
* **[2026-11-22] CI-014 Code pane per page implementation:** The `(planned)` Code pane per page, Page pane, Add page, Syntax errors per pane and Implicit page root decisions are confirmed as implemented, with these clarifications. (1) Each pane is a bordered box with a header row (`Page:` title input, `Id:` id input) and a monospace text area, labelled `Page N title`, `Page N id` and `Page N source`; `+ Add Page` (an outline button) is centred under the panes. (2) A header error (duplicate id, a title with a straight quote) is shown under its pane with the bare message; a content error is shown as `Line <n>: <message>` with `n` counted within the pane, and a nested `Page` shows `Line <n>: Page cannot be written here, it is created from the title and id` (the line prefix is kept, as for every content error). (3) The title and id fields are not trimmed or validated by the editor: whatever is typed is written into the `Page` line and the parser reports what it cannot read. (4) Whitespace-only lines of a pane are kept exactly as typed (they are neither indented nor unindented), so spaces typed on an empty line are not swallowed while the user types an indented line. (5) A trailing newline typed in a pane is kept (it is not trimmed), so Enter works at the end of a pane. (6) Blank lines before the first `Page` line of a stored source are dropped; any other text before it goes first in the first pane. (7) The `Feature detail` sketch in `features-list.ts` puts the source lines directly in each page's bordered box, below the `Page:`/`Id:` `BoxRow`, with no inner box for the text area.
* **[2026-11-22] CI-014 Parse of the joined pages:** This amends `CI-014 Syntax errors per pane (planned)`, which says the parser runs on the whole source. The editor parses `joinSourcePages(splitSourcePages(source))` rather than the stored `source` itself, so the line numbers of the parser's error always match the panes it is mapped to. For every valid source this gives the same AST, and for a source the panes cannot show exactly as stored (for example text before the first page, or a line indented by one space) the panes show what will be saved on the next edit. The first edit in any pane saves that joined text.
* **[2026-11-22] Collapsible page panes:** Each page pane's source can be collapsed and expanded, like an accordion. The pane's header row (`Page:` title field, `Id:` id field) always stays visible, with a toggle (chevron) button at its right end that shows or hides the pane's text area. Every pane is collapsed when the details page is opened (so navigating to a feature, or away and back, starts collapsed again), panes open and close independently of each other (several can be open at once) and the open state is not saved. A page added with `+ Add Page` starts expanded so it can be filled in straight away. A syntax error stays visible under its pane even while the pane is collapsed, so an error is never hidden. Collapsing does not change the source, the preview or the selected tab. This amends `CI-014 Page pane (planned)`, which showed every text area.
* **[2026-11-22] First page pane expanded initially:** This amends `Collapsible page panes`: when the details page is opened, the first page's pane is expanded and every other pane is collapsed (instead of all collapsed). Everything else in `Collapsible page panes` is unchanged, including that the blank source's single pane is therefore expanded.
* **[2026-11-22] Mock data persisted in local storage:** This amends `CI-007 Mock API (planned)` and `CI-008 Wire frame per feature (planned)`, which say the mock data lives in memory only and resets on reload. Every feature created and every wire frame saved through the mock API is now kept in the browser's local storage, so it is still there after the page is reloaded or the app is restarted. When local storage holds no features when the app starts (nothing stored, or stored data that is not a valid list of features), it is filled with the three seeded features first. Once something is stored the seed is never applied again, so seeded features are not restored if the user's data is changed; clearing the site's local storage brings the seed back.
* **[2026-11-23] CI-016 Data dictionary pane on the details page (planned):** This extends `CI-008 Details page layout`: below the wire frame source and wire frame cards the details page shows a data dictionary pane that spans the full width of the page, as wide as the two cards together, with the `Data dictionary` heading. The wire frame cards, the page heading and the other pages are unchanged. The unknown-feature page shows no data dictionary.
* **[2026-11-23] CI-016 Static details layout (planned):** This amends `CI-008 Details page layout` and `CI-016 Data dictionary pane on the details page (planned)`. The feature details page is a static layout: it fills the whole window (below the top nav) and never shows a page scroll bar, at any window size. From top to bottom it has (1) the back link, the `Feature: <name>` heading and the description, at their natural height; (2) the `Wireframe` heading and the wire frame source and wire frame cards side by side, which take all the height that is left; (3) the data dictionary pane at the bottom, at its fixed height of 5 rows (see `CI-016 Fixed-height pane (planned)` in the `data-dictionary` capability). The two wire frame cards are each as tall as the area they share, and the content of each scrolls inside its card when it is taller than the card (the page panes with their `+ Add Page` button in the source card; the page tabs and preview in the wire frame card), with the card titles staying visible. When the window is narrow the cards still stack, and then share the available height equally, each scrolling on its own. When the window is so short that nothing is left for the cards, they shrink rather than the page scrolling. The features list page and the unknown-feature page are not part of this change.

## Technical Decisions
* **[2026-11-21] CI-007 Routing (planned):** Client-side routing with `react-router` (declarative `BrowserRouter`, `Routes`, `Route`, `Navigate`), added with `pnpm add react-router`. `src/main.tsx` mounts the router and `src/App.tsx` becomes the route table; the current `App` content moves unchanged into a `WireframeDemo` component (`src/pages/wireframe-demo.tsx`) and the features page lives in `src/pages/features.tsx`. `<Toaster />` is mounted once in `App.tsx` (outside the routes) so both pages share it. Because the production site is a single-page app, a `public/_redirects` file (`/* /index.html 200`) is added so deep links such as `/features` work on Netlify.
* **[2026-11-21] CI-007 Feature schema (planned):** A `Feature` is defined with Zod in `src/features/schema.ts`: `FeatureSchema = z.strictObject({ id, name, description, createdAt })` and `CreateFeatureInputSchema = z.strictObject({ name, description })`, with types derived through `z.infer`. The schema is the single source of truth for what the API accepts and returns; the modal validates the form input with `CreateFeatureInputSchema` (after trimming) and shows the first error message.
* **[2026-11-21] CI-007 Mock API implementation (planned):** `src/features/api.ts` exports `listFeatures(): Promise<Feature[]>` and `createFeature(input): Promise<Feature>`, the only way the UI reads or writes features. They operate on a module-level in-memory array seeded with a few features, resolve after a short delay, return copies (never the stored objects), validate the input with `CreateFeatureInputSchema` (rejecting with an `Error` carrying the message) and generate `id` (`crypto.randomUUID()`) and `createdAt` (ISO string). A `resetMockFeatures()` helper restores the seed and a `delay` setting of 0 is used in tests so no fake timers are needed.
* **[2026-11-21] CI-007 UI components (planned):** The modal uses the shadcn `dialog`, `input` and `label` components (added with `pnpm dlx shadcn@latest add dialog input label`) together with the existing `button`, `card` and `textarea`. Page state (loading, error, list, modal open) is held with React state in the features page; no data-fetching library is added. The list and form logic that does not need a DOM (validation of the form values, adding a created feature to the list) is kept in pure functions so it can be tested without a DOM, as in the viewer.
* **[2026-11-21] CI-007 Page state (planned):** This amends `CI-007 UI components (planned)`: following `CI-007 No list states (planned)`, the features page state is only the list (initially empty) and whether the modal is open. The list is loaded once on mount with `listFeatures()`, with no loading or error flags.
* **[2026-11-21] CI-007 Routing implementation:** Implemented as planned, with `react-router` 8 added by `pnpm add react-router`. The route table is exported as data, `appRoutes: RouteObject[]` in `src/App.tsx`, and `App` renders it with `useRoutes` next to the single `<Toaster />`; `src/main.tsx` wraps `App` in `BrowserRouter`. `/` and `*` are `<Navigate to="/features" replace />` routes. `public/_redirects` is added. The routing test uses `MemoryRouter` with `renderToStaticMarkup` for `/features` and `/wireframe-demo`; because a static render does not run effects, a `Navigate` cannot be followed there, so the redirects are tested by matching `appRoutes` with `matchRoutes` and asserting the matched route is a `Navigate` to `/features`.
* **[2026-11-21] CI-007 Schema implementation:** `src/features/schema.ts` as planned: `FeatureSchema` and `CreateFeatureInputSchema` are `z.strictObject`s sharing a `name` schema that refines "non-empty after trimming" with the message `Name is required`; `id` and `createdAt` are non-empty strings. The schema validates but does not transform: trimming is done by the form (`validateFeatureForm`) and by the API when storing.
* **[2026-11-21] CI-007 Mock API implementation:** Implemented as planned in `src/features/api.ts` (`listFeatures`, `createFeature`, `resetMockFeatures`). The delay is controlled by `setMockDelay(ms)` (tests use 0); `resetMockFeatures()` also restores the default 400 ms delay. Invalid input rejects with an `Error` whose message joins the schema issue messages.
* **[2026-11-21] CI-007 UI implementation:** The shadcn `dialog`, `input` and `label` components were added with `pnpm dlx shadcn@latest add dialog input label` (`src/components/ui`). The page (`src/pages/features.tsx`) holds only the list and the modal's open flag, loads the list once on mount (ignoring a result that arrives after unmount) and shows a toast on creation. The modal is `CreateFeatureDialog` (`src/features/create-feature-dialog.tsx`), which owns the form values, error and `creating` flag, calls `createFeature` and reports the new feature through `onCreated`; closing it by any route (Cancel, the close button, Escape) clears the values and error. The list is `FeatureList` (`src/features/feature-list.tsx`). The DOM-free logic is in `src/features/logic.ts`: `validateFeatureForm` (trims, validates with `CreateFeatureInputSchema`, returns the first message) and `appendFeature`. Tests: `schema.test.ts`, `api.test.ts`, `logic.test.ts` and `src/pages/features.test.tsx`; the modal's interactions (opening, submitting, closing) are not DOM-tested, only the logic behind them.
* **[2026-11-21] CI-007 Top nav implementation:** `TopNav` (`src/components/top-nav.tsx`) uses react-router `NavLink` (which sets `aria-current="page"` on the active item) and is rendered by `App` above the routes, next to `<Toaster />`. The `min-h-screen` on the two pages' `main` elements was removed so the nav does not cause a needless scroll. Tested in `src/pages/features.test.tsx` (links, labels and current item per route).
* **[2026-11-21] CI-007 Top nav shadcn component:** This supersedes the react-router `NavLink` markup in `CI-007 Top nav implementation`: the nav now uses the shadcn `navigation-menu` component (added with `pnpm dlx shadcn@latest add navigation-menu`, `src/components/ui/navigation-menu.tsx`), as the project's convention is to use shadcn components where one exists. Each item is a `NavigationMenuLink` rendered as a react-router `Link` (`render={<Link to=... />}`) styled with `navigationMenuTriggerStyle()`, and its `active` prop (set from `useLocation()`) provides the highlight and `aria-current="page"`. The behaviour and the test are unchanged.
* **[2026-11-21] CI-008 Feature schema (planned):** This extends `CI-007 Feature schema (planned)`: `FeatureSchema` gets `wireframe: z.string()` (the wire frame source, `""` allowed and meaning blank). `CreateFeatureInputSchema` is unchanged, so creating a feature always starts with `wireframe: ""` (set by the API, like `id` and `createdAt`). The wire frame source is stored as text and is not validated by the feature schema; the editor reports syntax errors while editing (parse errors do not stop the text being saved).
* **[2026-11-21] CI-008 Mock API (planned):** `src/features/api.ts` gains `getFeature(id): Promise<Feature | undefined>` and `updateFeatureWireframe(id, wireframe): Promise<Feature>` (rejecting with an `Error` for an unknown id). Both follow `CI-007 Mock API implementation (planned)`: in-memory, delayed, returning copies. The page keeps the source in React state as the editor's value and calls `updateFeatureWireframe` on every change; the calls resolve in order because they share the same delay, so the last edit wins. The editor never waits for the API.
* **[2026-11-21] CI-008 Wire frame source files (planned):** Each seeded feature's wire frame source lives in its own file in `src/features/wireframes/`, one `.ts` file per feature exporting a single source string (e.g. `wire-frame-editor.ts` exporting `wireFrameEditorSource`), and the seed in `src/features/api.ts` imports them. The first is the Login Form sample moved from `src/viewer/sample.ts` (which is removed, `sampleSource` has no other use); the other two are small samples for `Page links` (two pages linking to each other) and `Features list`. Features created at runtime have no file, only the `wireframe` field.
* **[2026-11-21] CI-008 Components (planned):** The source editor and preview move out of the removed `src/pages/wireframe-demo.tsx` into a `WireframeEditor` component (`src/viewer/wireframe-editor.tsx`) with props `source` and `onSourceChange`; it owns the parse result and the selected page tab, with no other change in behaviour. The details page is `src/pages/feature-details.tsx` (default export, reads `:id` with `useParams`) and the route table in `src/App.tsx` is updated. `FeatureList` renders the name as a react-router `Link`. `TopNav` loses the `Wireframe` item and treats `/features/*` as the `Features` item being current.
* **[2026-11-21] CI-008 Implementation:** The `(planned)` Feature schema, Mock API, Wire frame source files and Components decisions are confirmed as implemented, with these clarifications. ## Data Dictionary
- `SourcePage`: One page of a wire frame source as the editor shows it (UI-only, not stored or sent to the API): `title` (string, `""` allowed), `id` (string, `""` meaning no id) and `content` (string, the page's nodes as shown in its pane, from column 0 and without the page's 2-space indentation or the `Page` line, `""` when blank).
- `Feature.id`: Unique identifier of the feature (string, generated by the API).
- `Feature.name`: The feature's name (string, non-empty after trimming, required).
- `Feature.description`: The feature's description (string, may be `""`).
- `Feature.createdAt`: When the feature was created (ISO 8601 string, generated by the API).
- `Feature.wireframe`: The feature's wire frame source text (string, `""` for a blank wire frame; `""` for a newly created feature).
- `CreateFeatureInput`: What the create form sends to the API: `name` and `description` only.
