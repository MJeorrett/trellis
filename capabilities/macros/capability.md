# Capability: Macros

## User Need
As a Trellis author (human or AI agent), I want to define reusable UI macros once and use them many times so that I can write a wire frame as high-level building blocks (a form field, a card, a tab bar) instead of repeating the same structure of core primitives.

## Product Decisions
* **[2026-11-23] CI-017 Macro preprocessor (planned):** Macros are a structural preprocessor that runs before the core syntax is parsed. A macro is defined once with `Def` and used like a node type; before the wire frame is built, every use is replaced by the macro's body. The result is plain core syntax (`Page`, `Row`, `BoxRow`, `Box`, `Text`, `Image`, `Spacer`), so the wire frame, the AST, the preview and every other part of Trellis know nothing about macros. Pipeline: raw source, macro preprocessor, core parser (`parseSyntax`), renderer. This iteration delivers the preprocessor only; the planned built-in macros (`Field`, `Card`, `NavTabs`, `FieldList`) are not part of it and come in later iterations, written as `Def`s on top of it.
* **[2026-11-23] CI-017 Def syntax (planned):** A macro is defined at the root level (no indentation) with `Def <Name> [$param ...]`, followed by its body: one or more lines indented by exactly 2 spaces (more for nesting) written in core syntax, exactly as they would be inside a `Page` (see `/capabilities/trellis-ast/capability.md`). The body ends at the next line that is not indented (or the end of the source). `Def`s may appear anywhere at indent 0, before, between or after pages, and a `Def` produces no output of its own. A macro must be defined before the line that uses it (a use above its `Def` is an unknown type, reported by the core parser). `Def` is case-sensitive and cannot be indented. The macro name is Pascal case (`[A-Z][A-Za-z0-9]*`), unique across the source, and cannot be a core type name (`Page`, `Box`, `Text`, `Row`, `BoxRow`, `Spacer`, `Image`) or `Def`. Parameters are separated by exactly one space, each is `$` followed by a name of letters, digits and `_` starting with a letter (`$label`), and each name may appear once. A macro with no parameters is valid.
* **[2026-11-23] CI-017 Parameters in the body (planned):** A parameter is used in the body as the text of a line, in place of the quoted string (`Text $label`, `Box $value font=bold`), and is replaced by the quoted argument. It is valid only in that place: not as an attribute value, a type or inside a quoted string (`"$label"` is plain text, as everything inside quotes is). Every parameter used must be declared in the `Def` line. A declared parameter that the body never uses is allowed. A body line that uses a parameter and also has text of its own is not possible, since a line has one text position.
* **[2026-11-23] CI-017 Using a macro (planned):** A macro is used on a line of its own, at any indentation where the line it replaces could appear, written like a node: `<Name> key="value" ...`, with an argument for every parameter, written as the parameter name without the `$`, an `=` and a double-quoted string (same rules as node text: no escapes, so no `"` inside, and `""` is valid). Arguments are separated by exactly one space and may be in any order, each exactly once. There are no default values: every parameter needs an argument. A macro use cannot have children (an indented line under it is an error). In the example below, `Field label="First Name" value="Please enter First Name..."` is how the `Field` macro is used (the `Usage` word in the specification's example is only a label for it, not syntax).
* **[2026-11-23] CI-017 Expansion (planned):** The use line is replaced by the body: the body's lines keep their indentation relative to each other and are re-indented so that the body's first level sits at the use line's indentation, and each `$param` is replaced by the quoted argument. A body may have several first-level lines (they become siblings). The expansion is purely structural: it is not checked for meaning by the preprocessor, so the usual core rules apply to the result (for example a body that starts with `Spacer` used directly under a `Page` gives `Spacer must be inside a Row or BoxRow`, and a body that starts with a `Page` can only be used at indent 0). A macro body may use macros that are defined above it, so macros can be built from other macros. A macro cannot use itself or a macro defined below it, so there is no recursion.
* **[2026-11-23] CI-017 Errors (planned):** Like all syntax errors they are fail-fast, with a 1-based line number counted in the source as written (see `CI-017 Error lines (planned)`), prefixed `Line <n>: `. Messages: `Def must not be indented`; `Def requires a name`; `Invalid macro name "<name>" (expected Pascal case)`; `Macro name "<name>" is reserved`; `Duplicate macro "<name>"`; `Invalid parameter "<token>" (expected $name)`; `Duplicate parameter "$<name>"`; `Macro "<name>" has an empty body`; `Unknown parameter "$<name>" in macro "<name>"` (used in the body but not declared); `Parameter "$<name>" can only be used as text`; `Missing argument "<name>" for macro "<macro>"`; `Unknown argument "<name>" for macro "<macro>"`; `Duplicate argument "<name>"`; `Invalid argument "<token>" (expected name="value")`; and `Macro "<name>" cannot have children`. Body lines that are indented wrongly (a tab, an odd indent, or a body line indented by 1 space) use the core messages (`Tabs are not allowed`, bad indentation).
* **[2026-11-23] CI-017 Error lines (planned):** An error found by the core parser in the expanded text is shown at the line of the source the author wrote, not a line of the hidden expanded text: a problem in text that came from a macro is reported at the line that uses the macro, with the macro named, e.g. `Line 9: Spacer must be inside a Row or BoxRow (in macro "Field")`. Errors in text that is not from a macro are unchanged. The wire frame editor therefore keeps showing line numbers that match its text areas.
* **[2026-11-23] CI-017 No comments or defaults (planned):** The core syntax has no comment lines and this iteration does not add any: a line that begins with `#` is not a comment (it is an unknown type like any other text), so the `#` line in the specification's example is an annotation of the example only. There is no default-value syntax for parameters (see `CI-017 Using a macro (planned)`). Both can be added later through new decisions.
* **[2026-11-23] CI-017 Scope (planned):** Macros are available wherever wire frame source is parsed (the editor of a feature's details page and its preview). The seeded sample wire frames, the viewer, the AST schema and the data dictionary are not changed by this iteration. The `Features` and wire frame viewer capabilities keep working as before for sources without macros: a source with no `Def` and no macro use is parsed exactly as before.
* **[2026-11-23] CI-017 Parameters can be used anywhere (planned):** This supersedes `CI-017 Parameters in the body (planned)` and amends `CI-017 Using a macro (planned)`. A parameter is no longer limited to the text position: `$name` may be used anywhere on a body line (inside the quotes of the text, as an attribute value, an attribute key or the type), and every `$name` on the line is replaced by the argument's value. Because the value is stored without quotes, the body always writes its own quotes: text positions are quoted explicitly (`Text "$label"`) and attribute positions are left bare (`font=$font`), exactly as in core syntax, so the result is never double-quoted (`""Test label""`). A body line with a text position written without quotes (`Text $label`) is therefore not valid for a text argument: it expands to bare text, which the core parser rejects like any unquoted text. `$name` is the `$` followed by the longest run of letters, digits and `_` starting with a letter (so `$label_x` is the parameter `label_x`, and `$5` or a lone `$` are plain text). Every such `$name` on a body line must be declared in the `Def` line, even inside quotes (`Unknown parameter "$<name>" in macro "<macro>"`), so a literal `$name` cannot be written in a body. This removes the error `Parameter "$<name>" can only be used as text`.
* **[2026-11-23] CI-017 Argument values (planned):** This amends `CI-017 Using a macro (planned)`. An argument is written `name=value` where the value is either a double-quoted string (`label="Test label"`, same rules as node text: no `"` inside, `""` is valid, so it may contain spaces) or a bare value (`font=bold`) of one or more characters that are not spaces or `"`. Surrounding quotes are stripped when the value is stored, so `$label` is `Test label` and `$font` is `bold`; a bare value and the same value quoted are the same argument. Arguments are still separated by exactly one space, in any order, each exactly once, with no defaults. The invalid-argument message is now `Invalid argument "<token>" (expected name=value or name="value")`. Example: `Field label="Test label" font=bold` with the body line `Text "$label" font=$font` gives `Text "Test label" font=bold`.
* **[2026-11-23] Global macros page:** A new top-level `Macros` nav item, beside `Features`, opens the `/macros` page. The macros defined there are global: they are shared by every feature's wire frame (see `Global macros in features`). The page has a `Macros` heading and, like the feature details page, two cards side by side (stacked on a narrow window): on the left a single source text (one text area, with no page tabs and no `+` button) and on the right the wire frame that the text compiles to, so macros can be tried out. The source is the whole text: it holds the `Def`s and may also hold `Page`s that use them, which are only there to experiment with and are previewed on the right with the same page tabs as a feature's wire frame. A syntax error is shown above the text area with its 1-based line number in that text, and the preview then shows `Fix the source to see the wire frame.`. Every edit is saved automatically, with no save button, and is there on the next visit. Until something is saved, the page shows an example: a `Heading` macro (`Def Heading $text $size`) and a `Try it` page using it twice. A `Def` is not allowed to be indented anywhere in the text (see `CI-017 Errors (planned)`).
* **[2026-11-23] Global macros in features:** Only the `Def`s of the global macros text are shared; its `Page`s and any other lines are ignored outside the Macros page. Every feature's wire frame editor and preview compile their source with the global `Def`s defined above its first line, so a feature uses a global macro exactly like one of its own (`Heading text="Hi" size=lg`). A feature may also define its own macros, but a name already defined globally is a `Duplicate macro` error at the feature's own line, as for two `Def`s of a source. An error in the global text itself (for example an invalid `Def`) is shown on every feature page and on the Macros page, and on the feature pages it is prefixed `Macros: ` (`Macros: Line 3: Invalid macro name "a" (expected Pascal case)`), because its line numbers are those of the Macros page and not of the feature's source. Changes made on the Macros page are used by a feature page the next time it is opened. The feature's details page waits for the macros to load before showing the editor, so a use of a global macro never flashes as an unknown type. The seeded `Wire frame editor` wire frame keeps its own `Field` macro, so the global example must not be named `Field`.
* **[2026-11-23] Field in the seeded global macros:** This supersedes `CI-017 Seeded wire frame with a Def` and amends `Global macros page` and the last sentence of `Global macros in features`. The seeded wire frames carry no macros again: the `Wire frame editor` wire frame is back to the hand-written Log in page (the same AST as before), so `parseSyntax` parses all three seeds, and the tests that parse the seeds use it again. The example is instead the seed of the global macros: `Def Field $label $value` (a `Box` with the `Text "$label"` in bold and a `Box "$value"`) and a `Try it` page using it for `Email` and `Password`; this replaces the `Heading` example. Because no seeded wire frame defines `Field`, there is no duplicate with the global one.
* **[2026-11-23] Unlabeled argument $1:** This extends `CI-017 Using a macro (planned)`, `CI-017 Argument values (planned)` and `CI-017 Parameters can be used anywhere (planned)` with one unlabeled (positional) argument, so that a macro with a single main value reads like core syntax, whose text comes right after the type: `Def PageTitle` with the body `Text "$1" font=bold font-size=lg` is used as `PageTitle "My Page"` and gives `Text "My Page" font=bold font-size=lg`. (1) `$1` is the unlabeled argument. It is used in a body like any other `$name` (anywhere on a body line, as many times as needed, and passed on to a nested macro as `Inner "$1"`) and is replaced by the argument without its quotes, so the body writes its own quotes. (2) It is not declared on the `Def` line: a macro that mentions `$1` in its body requires it, and a macro that does not mention it does not accept it. `$1` cannot be written as a parameter (`Def A $1` is `Invalid parameter "$1" (expected $name)`). (3) At a use it is written first, directly after the macro name and before any named argument, as a quoted string or a bare value with the same rules as a named argument's value (`PageTitle "My Page"`, `PageTitle Home`, `PageTitle ""`; a bare value has no spaces, `"` or `=`), and it can be followed by named arguments in any order (`Field "First Name" value="x" font=bold`). There is at most one, and it cannot come after a named argument. (4) New errors: `Missing positional argument for macro "<name>"` and `Unexpected positional argument for macro "<name>"` (the macro does not mention `$1`). A second or late unlabeled token is the existing `Invalid argument "<token>" (expected name=value or name="value")`, and `1=value` is `Unknown argument "1" for macro "<name>"`. (5) `$1` is only the exact text `$1`: `$12`, `$1a`, `$1_` and `$0` are plain text, like any `$` not followed by a parameter name, but a literal `$1` can no longer be written in a body.
* **[2026-11-23] CI-019 Object parameters (planned):** A parameter can be an object: one named value made of several fields, so that a macro can take a whole record (a card's title, description and id) as one parameter. On the `Def` line it is written `$name=field|field|...` (`Def Card $item=title|description|id`): the parameter name follows the usual `$name` rules, and the fields follow `=`, separated by `|` with no spaces; each field name is letters, digits and `_` starting with a letter, unique within the parameter, and there is at least one. Plain parameters (`$label`) are unchanged and may be mixed with object parameters on the same `Def` line. In the body a field is written `$item.title`, anywhere a `$name` may appear (see `CI-017 Parameters can be used anywhere (planned)`), and is replaced by that field's value; as everywhere, the body writes its own quotes (`Text "$item.title"`). A field reference is `$` plus the parameter name, `.`, and the longest run of letters, digits and `_` starting with a letter. For a plain parameter nothing changes: in `$label.x` the `$label` is replaced and the `.x` stays text. For an object parameter the bare form (`$item` with no `.field`, or `$item.` followed by something that is not a field name) is an error, as is a field that the `Def` does not declare. Like every `$name`, a field reference must name a declared parameter, even inside quotes, so a literal `$item.title` cannot be written in a body of a macro that declares `$item` as an object.
* **[2026-11-23] CI-019 Object arguments (planned):** This extends `CI-017 Using a macro (planned)` and `CI-017 Argument values (planned)`. The argument for an object parameter can be written in two forms. (1) Dotted, one named argument per field: `Card item.title="Hi" item.description="Text" item.id="1"`; each is a normal named argument (a double-quoted string or a bare value, same rules as other named arguments), in any order, each exactly once, separated by exactly one space like the others. (2) Piped, one argument with the values in the order the fields are declared on the `Def`: `Card item="Hi"|"Text"|"1"`. Each value is a double-quoted string (which may contain `|` and spaces, `""` is valid) or a bare value of one or more characters that are not spaces, `"` or `|`; values are separated by `|` with no spaces around it. As for other arguments, the quotes are stripped when the value is stored, so `item="Hi"|Text|"1"` is `Hi`, `Text` and `1`. An object parameter needs all its fields, by either form: there are no defaults, and writing a field both ways, or both forms for the same parameter, is a duplicate. The forms can be combined with the unlabeled `$1` argument and with plain named arguments in any order after it. Examples of the same use: `Card item.title="Hi" item.description="Text" item.id="1"` and `Card item="Hi"|"Text"|"1"`, for the body `Text "$item.title"`, `Text "$item.description"`, `Text "$item.id"`.
* **[2026-11-23] CI-019 Errors (planned):** New fail-fast errors, prefixed `Line <n>: ` like the other macro errors. On the `Def` line: `Invalid parameter "<token>" (expected $name or $name=field|field)` for a malformed object parameter (an empty field, a bad field name, no field after `=`; this replaces `Invalid parameter "<token>" (expected $name)` for parameter tokens), `Duplicate field "<field>" in parameter "$<name>"`, and the existing `Duplicate parameter "$<name>"`. In the body: `Parameter "$<name>" is an object (use $<name>.<field>)` for a bare object parameter and `Unknown field "<field>" on parameter "$<name>"` for an undeclared field. At a use: `Missing argument "<name>.<field>" for macro "<macro>"` (a field not given), `Unknown argument "<name>.<field>" for macro "<macro>"` (a field the parameter does not have), `Duplicate argument "<name>.<field>"` (given twice, or by both forms), `Parameter "<name>" expects <n> values but got <m>` (piped form with the wrong number of values) and `Invalid argument "<token>" (expected name=value or name="value")` for a piped value that is malformed (such as an empty bare value in `item=a||b`). A plain named argument for an object parameter without a field (`item="x"`) is the piped form with one value, so it is a count error unless the object has exactly one field.
* **[2026-11-23] CI-019 Seeded global macros (planned):** This amends `Field in the seeded global macros`. The seed of the global macros text also defines `Def Card $item=title|description|id`, a `Box` containing the title in bold, the description and the id as `Text` lines, and the `Try it` page also shows two cards, one written in each argument form. `Field` and its use stay as they are. The seeded feature wire frames are not changed and do not define `Card`, so there is no duplicate with the global one.
* **[2026-11-23] CI-019 Object parameters behaviour:** The `(planned)` `CI-019 Object parameters`, `CI-019 Object arguments`, `CI-019 Errors` and `CI-019 Seeded global macros` product decisions are confirmed as implemented, with these clarifications. (1) A dot after a plain parameter or `$1` is only text (`$label.x` is the value followed by `.x`), and text that continues a field name is part of it (`$item.title_x` is an unknown field `title_x`), while text after a complete field stays (`$item.title.x` is the title followed by `.x`). (2) A dotted argument for a plain parameter or for a field the object does not have is `Unknown argument "<name>.<field>"`. (3) The seed of the global macros has the `Card` macro (a `Box` with the title in bold, then the description and the id as `Text` lines) and its `Try it` page shows `Field` twice, then a card per argument form: `Card item.title="Welcome" item.description="Say hello to the team" item.id="1"` and `Card item="Reports"|"See how the team is doing"|"2"`.

## Technical Decisions
* **[2026-11-23] CI-017 Module layout (planned):** The preprocessor is a pure, DOM-free module, `src/web/syntax/macros.ts`, exporting `expandMacros(source: string): ExpandResult`, with `ExpandResult = { ok: true; source: string; origins: LineOrigin[] } | { ok: false; error: string }`. `origins[i]` says, for line `i` (0-based) of the expanded `source`, the 1-based line of the original source it came from and the macro name when it came from a macro body (`{ line: number; macro?: string }`); lines that were kept from the original have `line` equal to their own original line. The `Def` blocks are removed from the expanded text. The core parser, `parseSyntax` in `src/web/syntax/parse.ts`, is not changed and does not import the preprocessor, so it stays unaware of macros.
* **[2026-11-23] CI-017 Compile entry point (planned):** A new `compileSyntax(source: string): ParseResult` in `src/web/syntax/compile.ts` runs `expandMacros`, then `parseSyntax` on the expanded text and, on a core error, rewrites the `Line <n>:` prefix of the error using `origins` (the line within the expanded text becomes the original line, and ` (in macro "<Name>")` is appended when the line came from a macro body). A preprocessor error is returned as it is. `ParseResult` is the existing type. Consumers that parse a wire frame source (`WireframeEditor`) call `compileSyntax` instead of `parseSyntax`; nothing else changes. A schema error without a line number (a `AstSchema` failure such as a duplicate page id from expanded text) is passed through unchanged, as today.
* **[2026-11-23] CI-017 Definitions with Zod (planned):** The parsed definitions are validated with Zod, as the rest of the project: `MacroNameSchema` (`z.string().regex(/^[A-Z][A-Za-z0-9]*$/)` and not a reserved name), `ParamNameSchema` (`z.string().regex(/^[A-Za-z][A-Za-z0-9_]*$/)`) and `MacroDefinitionSchema = z.strictObject({ name, params: z.array(ParamNameSchema), body: z.array(z.string()).min(1) })`, with the types derived through `z.infer`. They are used inside `macros.ts` only; nothing is added to the AST schema (`src/web/schema/ast.ts`), because macros never reach the AST. The reserved names come from `NodeTypeSchema.options` plus `Page` and `Def`, so a new core type is reserved automatically.
* **[2026-11-23] CI-017 Algorithm (planned):** One pass over the lines: a line that starts with `Def ` at indent 0 begins a definition, whose body is the following lines that are blank or start with a space; the definition is registered (in definition order) and its lines are dropped. Any other line is looked at only for its type word: if that word is a defined macro name the line is a macro use, which is parsed (arguments, children check by looking at the next non-blank line's indentation), expanded and the result is itself scanned so that a macro body may use earlier macros (a depth limit is not needed because a body can only refer to macros defined above it). Every other line is kept as is, including blank lines, so the core parser's behaviour on macro-free sources is identical to today. Substitution of a parameter is a replace of the text token on the line, never inside a quoted string.
* **[2026-11-23] CI-017 Substitution (planned):** This supersedes the last sentence of `CI-017 Algorithm (planned)` (substitution never inside a quoted string) for `CI-017 Parameters can be used anywhere (planned)`. Arguments are parsed into a `Record<string, string>` of unquoted values (the quotes of a quoted argument are removed once, when it is parsed, and never added back by the preprocessor). Substitution is a single `String.replace` over each body line with the pattern `/\$([A-Za-z][A-Za-z0-9_]*)/g`, a function replacer looking the name up in that record (so a value that itself contains `$name` is not substituted again). Declared-parameter checking is done once when the `Def` is read, by scanning its body lines with the same pattern. Nested macro uses are expanded after the outer macro's substitution, so an outer parameter can be passed on (`Field label="$title"`).
* **[2026-11-23] CI-017 Preprocessor implementation:** The `(planned)` Module layout, Compile entry point, Definitions with Zod, Algorithm and Substitution decisions are confirmed as implemented, with these clarifications. (1) `macros.ts` also exports the three schemas and the `MacroDefinition`, `LineOrigin` and `ExpandResult` types for the tests; arguments are kept in a `Map` rather than a `Record`. (2) Each macro is registered with a snapshot of the macros defined above it, and its body (including nested uses) is expanded only with that snapshot, which is what stops self use and use of a macro defined below it. (3) A source with no `Def` and no macro use is returned as the very same string (so even CRLF text is unchanged). (4) A `Def`'s body is its following lines that are blank or start with a space; blank lines are dropped from the body and from the output, and a body line indented by exactly one space is kept with that odd indent so the core parser reports it. (5) Every line produced by an expansion, nested or not, is reported at the line of the outermost use; its `macro` is the macro whose body holds the line (the inner macro for a nested one). (6) Argument parsing uses one sticky pattern, so an error names the token up to the next space (`Invalid argument "a="x"`); the use line's trailing spaces are ignored. (7) The check order for a use is: arguments in the order written (invalid, unknown, duplicate), then missing, then `cannot have children`. (8) An indented `Def` is reported anywhere outside a `Def` body.
* **[2026-11-23] CI-017 Seeded wire frame with a Def:** This amends `CI-017 Scope (planned)`, at the user's request, so that the macro is visible in the app: the seeded `Wire frame editor` feature (`src/web/features/wireframes/wire-frame-editor.ts`) now starts with `Def Field $label $value`, a labelled box, and its Log in page uses it for the Email and Password fields. It compiles to exactly the AST of the hand-written wire frame, so the preview is unchanged. The Def is above the first `Page`, so it is shown in the first source tab. Because `parseSyntax` is unaware of macros, the tests that parse the seeded sources (`parse.test.ts`, `source-pages.test.ts`, `api.test.ts`) use `compileSyntax`. The sketched `Feature detail` page of the `Features list` feature, which shows the Log in source, is not changed.
* **[2026-11-23] Global macros implementation:** (1) `expandMacros(source, shared = "")` and `compileSyntax(source, sharedMacros?)` take the global text: its `Def`s are registered (in order, each seeing the ones above it) before the first line of `source`, and its other lines are ignored; an error in it is returned as `Macros: ` plus the usual `Line <n>: <message>`. `origins` and the line mapping describe the source only. With an empty or absent shared text the result is exactly as before. (2) The text is kept by a mock API, `src/web/macros/api.ts`, like the data dictionary: `getMacros(): Promise<string>`, `saveMacros(source): Promise<string>` (any string), `resetMockMacros()`, `setMockDelay(ms)` and the exported `MACROS_STORAGE_KEY` (`trellis.macros`) and `seedMacrosSource`. The text is stored raw in local storage through `src/web/lib/storage.ts`; a missing value (nothing saved yet) gives the seed, while a saved empty text stays empty. (3) `MacroEditor` (`src/web/macros/macro-editor.tsx`, props `source` and `onSourceChange`) is the text area, error and preview, and `MacrosPage` (`src/web/pages/macros.tsx`, with `MacrosView` for static rendering) loads the text, updates its state immediately on every change and saves without waiting (a rejection is ignored), as the details page does. (4) `WireframeEditor` and `FeatureDetailsView` take an optional `sharedMacros` prop, loaded by `FeatureDetailsLoader` with `getMacros()`, which shows nothing until both the feature and the macros have loaded. (5) The route is added to `appRoutes` as `MACROS_PATH` (`/macros`) and the nav item to `navItems`. (6) Tests: `api.test.ts` and `macro-editor.test.tsx` in `src/web/macros/`, shared-macro cases in `macros.test.ts`, and the nav, route and details view checks in `src/web/pages/features.test.tsx`; typing into the text area is not DOM-tested (`renderToStaticMarkup`).
* **[2026-11-23] Unlabeled argument implementation:** `MacroDefinitionSchema` gains `positional: z.boolean()`, set when the `Def` is read if any body line mentions `$1`. The substitution pattern becomes `/\$(1(?![A-Za-z0-9_])|[A-Za-z][A-Za-z0-9_]*)/g`, and the unlabeled argument is stored in the same argument `Map` under the key `"1"` (which no declared parameter can have, since parameter names start with a letter). `parseArguments` tries the labeled pattern first and only at the first argument (position 0) tries one more sticky pattern, `"..."` or `[^ "=]+` followed by a space or the end, for the unlabeled one; anywhere else a token that is not `name=value` stays an `Invalid argument`. The missing-positional check comes before the missing-named check. `parseSyntax`, `compileSyntax` and the line mapping are unchanged. Tests: the `the unlabeled argument $1` group and the new error cases in `macros.test.ts`.
* **[2026-11-23] CI-019 Object parameters implementation (planned):** In `src/web/syntax/macros.ts`, `MacroDefinitionSchema` gains `objects: z.record(ParamNameSchema, z.array(FieldNameSchema).min(1))`, a map from an object parameter's name to its ordered field list (empty for a macro with no object parameters), and `params` still lists every parameter name, plain or object, in declaration order. `FieldNameSchema` has the same pattern as `ParamNameSchema`. The `Def` line parser splits each parameter token on the first `=`; the part after it is split on `|`. ## Syntax

```
Def Field $label $value $font
  BoxRow
    Text "$label" font=$font
    Box "$value"

Page "Profile"
  Field label="First Name" value="Please enter First Name..." font=bold
  Field label="Last Name" value="Please enter Last Name..." font=bold
```

expands, before the core parser sees it, to:

```
Page "Profile"
  BoxRow
    Text "First Name" font=bold
    Box "Please enter First Name..."
  BoxRow
    Text "Last Name" font=bold
    Box "Please enter Last Name..."
```

Grammar (informal): `source = (def | line)*`, `def = "Def" " " MacroName (" " param)* NL (indent1 core-line NL)+` where `core-line` is core syntax in which any `"$" ident` may appear anywhere on the line (the text is written with its own quotes, `Text "$label"`, and attribute values bare, `font=$font`), `param = "$" ident`, `MacroName = [A-Z][A-Za-z0-9]*` (not a core type name or `Def`), `ident = [A-Za-z][A-Za-z0-9_]*`, and a macro use is `line = indent MacroName (" " ident "=" (quoted | bare))*` with exactly one argument for each parameter, `bare = [^ "]+`. The quotes of a `quoted` argument are stripped when it is stored. In addition, a macro whose body mentions `$1` takes one unlabeled argument first: `line = indent MacroName [" " (quoted | bare-no-equals)] (" " ident "=" (quoted | bare))*`, stored as `$1`; for example

```
Def PageTitle
  Text "$1" font=bold font-size=lg

Page "Home"
  PageTitle "My Page"
```

expands to `Text "My Page" font=bold font-size=lg` under the page.

An object parameter groups several values under one name, `param = "$" ident ["=" field ("|" field)*]` with `field = ident`, and is used as `$name.field` in the body; at a use its fields are given either one by one, `name.field=value`, or together, `name=value("|"value)*`, in the order declared (each `value` is `quoted | [^ "|]+`):

```
Def Card $item=title|description|id
  Box
    Text "$item.title" font=bold
    Text "$item.description"
    Text "$item.id"

Page "Cards"
  Card item.title="Hi" item.description="Text" item.id="1"
  Card item="Hi"|"Text"|"1"
```

Both uses expand to the same `Box` with `Text "Hi" font=bold`, `Text "Text"` and `Text "1"`.

## Data Dictionary
- `MacroDefinition`: One `Def`, existing only during preprocessing (never stored, never in the AST): `name`, `params` and `body`.
- `MacroDefinition.name`: The macro's name (Pascal case, unique, not a core type name or `Def`).
- `MacroDefinition.params`: The parameter names, without the `$` and without any `=field|...` part, in the order they are declared (may be empty). Plain and object parameters are both listed.
- `MacroDefinition.objects`: The object parameters of the macro: a map from a parameter's name (as in `params`) to its field names in declared order. Empty when the macro has no object parameters.
- `MacroDefinition.positional`: Whether the body mentions `$1`, so that a use needs (and accepts) one unlabeled argument.
- `MacroDefinition.body`: The body's lines with the 2-space indentation of the `Def` removed (at least one line).
- `Argument value`: The value given for a parameter at a macro use (or, for `$1`, the unlabeled argument, or, for a field of an object parameter, the value stored under `name.field`), stored without surrounding quotes (`label="Test label"` gives `Test label`, `font=bold` gives `bold`), existing only during preprocessing.
- `LineOrigin`: For one line of the expanded text, the original `line` (1-based) it is reported at and the `macro` it came from, when it came from a macro body.
