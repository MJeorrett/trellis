# Capability: UI AST (Abstract Syntax Tree)

## User Need
As a Trellis AI Agent, I need a deterministic, strictly typed JSON schema to represent UI wireframes so I can seamlessly translate visual layout into executable code and diagrams without hallucinating.

## Product Decisions
* **[2026-11-20] Component Library:** There is no component library - initially it is just `Box` and `Text` - both the same except `Text` doesn't have a border.
* **[2026-11-20] Authoring Syntax:** The AST gets a custom, indentation-sensitive text syntax as its authoring format, kept as minimal as possible (see [Syntax](#syntax)). It is parsed into the JSON AST, which stays the canonical, Zod-validated representation. Rationale: the JSON form is noisy for humans and agents to write (ids, empty `text`, empty `children`), while the text form carries only the information that matters.
* **[2026-11-20] Syntax Structure:** One node per line: `<Type> [text]`. Nesting is expressed solely by indentation (no braces, no closing tokens). Indentation is exactly 2 spaces per level; tabs and odd or skipped levels are errors. There is exactly one root node (the first non-blank line, at indent 0), except that a source with no nodes at all is a blank wire frame (see Blank Source). Blank lines are ignored.
* **[2026-11-20] Syntax Text:** The optional text after the type is either a double-quoted string (`Box "Some Text"`) or omitted (`Box`, meaning `""`). Nothing else is allowed: bare unquoted text (`Box Some Text`) is an error. There are no escape sequences for now: the text runs from the opening `"` to the next `"`, so it cannot itself contain a double quote, and anything after the closing quote is an error. `""` is valid and equals omitted text.
* **[2026-11-20] No Ids:** Nodes have no `id`, in the syntax or in the AST. Nothing needs to reference a node yet (the only consumer was the viewer's `data-node-id` attribute and React `key`, and a child index is enough for a static tree). This supersedes the CI-001 decisions on `id` (non-empty string, uniqueness check in `AstSchema`); the schema change is made in CI-003. Ids can be reintroduced (e.g. an optional explicit id in the syntax) when a capability needs cross-references, diffing or traceability.
* **[2026-11-20] Syntax Errors:** The parser fails fast with the first error, reported with a 1-based line number (e.g. unknown type, bad indentation, multiple roots, unterminated string). The parser's output is still passed through `AstSchema`, so the schema remains the single source of truth for validity. Errors are reported clearly in the Editor UI.
* **[2026-11-20] CI-003 Blank Source:** Empty or whitespace-only source is not an error: it parses to a blank wire frame, the root `{ type: "Text", text: "", children: [] }`. `Text` is used because it renders without a border, so a blank editor shows a blank wire frame rather than an empty box; the AST keeps its single-root invariant and no nullable AST is needed. This amends the "exactly one root" rule in Syntax Structure: a source with no nodes yields this implicit root, while a source with nodes must still have exactly one explicit root. It also supersedes the CI-003 acceptance criterion that rejected empty input.
* **[2026-11-20] CI-003 Strictness details:** Tabs are rejected anywhere in a non-blank line (including inside quotes). The type must be followed by nothing or exactly one space and then a quoted string, so `Box  "x"` (two spaces) is an error. Whitespace after a closing quote counts as trailing characters. A `Box ` with only trailing whitespace is treated as omitted text. Indentation is checked (tab, then multiple of 2) before the type, and a first line with indentation is reported as "first node must not be indented"; a later unindented line is "multiple root nodes". Type names are case-sensitive.
* **[2026-11-20] CI-003 Login Form sample:** The sample in the iteration (and in the viewer) uses a 9-character `"*********"` password placeholder, as in the Syntax section below.
* **[2026-11-20] CI-004 Row:** A new `Row` component type is added. It works exactly like `Box` (bordered, optional text, may have children) except that its children are laid out on a single row, left to right, in order. Children never wrap onto a new line, even if they overflow. This extends the Component Library decision (now `Box`, `Text` and `Row`). In the syntax `Row` is a type keyword used like `Box` (`Row`, `Row "Some Text"`), type names remain case-sensitive, and `Row` follows all existing syntax rules and errors.

* **[2026-11-20] CI-005 Page (planned):** A new `Page` component describes one complete page of the wire frame. It is the only valid root-level component and the root is always a `Page`: `Box`, `Text` and `Row` can no longer be roots. A `Page` cannot be nested anywhere (no subpages, not inside another `Page`, `Box` or `Row`). The direct children of a `Page` must be `Row`, `Box` or `Text` nodes, which keep their existing behaviour and nesting rules. A `Page` with no children is valid (it is a blank page). This extends the Component Library decision (now `Page`, `Box`, `Text` and `Row`).
* **[2026-11-20] CI-005 Page title (planned):** `Page` takes required title, written with the same quoted string used for text (e.g. `Page "Log in"`). The title is not rendered as content inside the page; the viewer uses it as the page's tab label. Implicit Page produced by a blank source has a title "Default".
* **[2026-11-20] CI-005 Multiple pages (planned):** A source may contain several `Page` nodes, each at indent 0, one after another. This supersedes the "exactly one root node" rule in Syntax Structure and the "multiple root nodes" error: multiple indent-0 nodes are now valid as long as each is a `Page`. Every other rule (2-space indentation, one node per line, blank lines ignored) is unchanged.
* **[2026-11-20] CI-005 Syntax errors (planned):** An indent-0 node that is not a `Page` is an error (e.g. `Line 1: root node must be Page`). A `Page` at any indent greater than 0 is an error (e.g. `Page cannot be nested`). Both are reported fail-fast with a 1-based line number like all other syntax errors. Sources without a `Page` root, such as the current Login Form sample, are therefore no longer valid and must be wrapped in a `Page`.
* **[2026-11-20] CI-005 Blank Source (planned):** This supersedes the CI-003 Blank Source decision: empty or whitespace-only source still is not an error, but it now parses to one blank page (empty title, no children) instead of a root `Text` node. The AST therefore always has at least one page and the viewer always has a page to show.
* **[2026-11-20] CI-005 Page implementation:** The `(planned)` Page, Page title, Multiple pages, Syntax errors and Blank Source decisions are confirmed as implemented, with these clarifications. (1) The blank source's page has an empty title `""`, as in CI-005 Blank Source and the iteration; this amends the "Default" title mentioned in CI-005 Page title (planned), which is not used. The viewer labels it `Page 1`. (2) Page-related errors are exactly `Line <n>: root node must be Page` (an indent-0 line whose type is not `Page`, including unknown or lowercase names such as `page`), `Line <n>: Page cannot be nested` (a `Page` at any indent greater than 0, checked before the first-node-indentation check) and `Line <n>: Page requires a title` (`Page` with nothing, or only whitespace, after it). A `Page` title follows the same quoted-string rules and errors as node text (unterminated string, trailing characters, bare unquoted text). (3) An indented non-`Page` first line is still reported as `The first node must not be indented`. (4) The "multiple root nodes" error is removed. (5) Within a page the existing rules apply unchanged; the indentation stack is reset at each new `Page`, so one page's depth never carries into the next.
* **[2026-11-20] CI-006 Attributes (planned):** A line can end with `key=value` attributes after the optional quoted text: `<Type> ["text"] [key=value]`. Attributes are separated from the type/text by exactly one space, the value is bare (not quoted) and must match `[A-Za-z0-9_-]+` (non-empty), and each key may appear at most once. For now there is a single attribute per component kind, so a line has at most one attribute. Text may be omitted before an attribute (`Box link-to=home`). A `Page` still requires its title first (`Page "Home" id=home`). The syntax errors (fail-fast, 1-based line number, like all others) are: an unknown attribute key (`Unknown attribute "foo"`), a duplicated key, a missing or invalid value (`Attribute "id" requires a value of letters, digits, `-` or `_``), and an attribute on a component that does not support it (`Box` cannot have id; `Page` cannot have link-to; `Row` cannot have link-to).
* **[2026-11-20] CI-006 Page id (planned):** `Page` may have an optional `id` attribute (`Page "My Page" id=test-id`) so that other components can link to it. `id` is valid on `Page` only; `Box`, `Text` and `Row` have no ids (this keeps the No Ids decision for nodes). Page ids must be unique across the source: a repeated id is an error reported at the line of the second page (`Duplicate page id "test-id"`). A page without an id cannot be linked to.
* **[2026-11-20] CI-006 Link target (planned):** `Box` and `Text` may have an optional `link-to` attribute whose value is the id of a page (`Text "My Link" link-to=test-id`). `Row` and `Page` cannot have `link-to`. A link to an id that no page has is not a syntax error: link targets are deliberately not validated by the parser, so a link may be written before its page exists. The viewer handles an unknown target when the link is clicked (see the `wire-frame-viewer` capability). Linked nodes keep their normal rendering and children; a linked `Box` or `Text` may contain other linked nodes (the innermost one wins on click).
* **[2026-11-20] CI-006 Links implementation:** The `(planned)` Attributes, Page id and Link target decisions are confirmed as implemented, with these clarifications. (1) The exact fail-fast errors (each prefixed `Line <n>: `) are: `Unknown attribute "<key>"`; `Duplicate attribute "<key>"`; `Attribute "<key>" requires a value of letters, digits, "-" or "_"` (missing value such as `id=`, or a value with other characters such as `a.b` or `"x"`); `<Type> cannot have <key>` (e.g. `Box cannot have id`, `Page cannot have link-to`, `Row cannot have link-to`); `Duplicate page id "<id>"`; and `Invalid attribute "<token>" (expected key=value)` for a further space-separated token without `=` (so `id=a b` is an invalid attribute `b`). (2) An attribute is recognised after the closing quote, or directly after the type when text is omitted, only when it has the shape ` <key>=...` with exactly one space; anything else after a closing quote keeps the existing `Unexpected characters after closing quote` error (so `Box "a"  link-to=x` with two spaces is that error). (3) Attribute-like content inside quotes is plain text. (4) `Page link-to=x` and `Page id=x` (no title) report `Page requires a title`, which is checked before the attribute errors. (5) Check order for a token: shape, then unknown key, duplicate key, whether the type supports the key, and finally the value.
* **[2026-11-22] CI-010 Spacer (planned):** A new `Spacer` component pushes its siblings apart inside a `Row`: it is invisible (no border, no text) and expands to fill all the remaining space in its `Row`. In `Text "A"`, `Spacer`, `Text "B"` the `A` is at the left end of the row and the `B` at the right end; a `Spacer` placed before an element pushes that element (and everything after it) to the right. When a `Row` has several spacers, the free space is shared equally between them. A `Row` without free space (children that already fill or overflow it) gives a `Spacer` no width. This extends the Component Library decision (now `Page`, `Box`, `Text`, `Row` and `Spacer`).
* **[2026-11-22] CI-010 Spacer syntax (planned):** In the syntax `Spacer` is a type keyword written alone on its line (`Spacer`), case-sensitive like other types. It cannot have text, attributes or children. The fail-fast errors (1-based line number, like all others) are: `Spacer must be inside a Row` (a `Spacer` that is not a direct child of a `Row`: directly in a `Page`, in a `Box`, in another `Spacer` or anywhere else), `Spacer cannot have text` (`Spacer "x"`), `Spacer cannot have <key>` for any attribute (e.g. `Spacer cannot have link-to`, following the existing `<Type> cannot have <key>` message) and `Spacer cannot have children` (an indented line under a `Spacer`). Wrapping a `Spacer` in a nested `Row` does not help: each `Spacer` fills only its direct parent `Row`.
* **[2026-11-22] CI-010 Sample (planned):** The Login Form sample in the first seeded feature (`src/features/wireframes/wire-frame-editor.ts`) puts a `Spacer` between `Box "Cancel"` and `Box "Submit"` in its `Row`, so the two buttons sit at opposite ends of the row.
* **[2026-11-22] CI-011 Width (planned):** `Box`, `Text`, `Row` and `Spacer` may have an optional `width` attribute (`Box "Email" width=3`) that sets the relative width of the element inside a `Row`, as a number of twelfths of the row: in a `Row` with a `width=3` child and a `width=9` child, the first takes 3/12 (1/4) of the row's width and the second 9/12 (3/4). `Page` cannot have `width`. Outside a `Row` (a direct child of a `Page`, a `Box` or a `Text`) `width` is valid syntax but has no effect; only the direct parent matters, so a `width` on a `Row` that is itself in a `Row` sets that inner row's share of the outer row, not the width of its own children.
* **[2026-11-22] CI-011 Width defaults (planned):** If no child of a `Row` has a `width`, the row is laid out as before (widths are left as is, and a `Spacer` fills the remaining space as in CI-010). If one or more children of a `Row` have a `width`, every child without one is treated as `width=3`, including a `Spacer`: in such a row a `Spacer` without a `width` is a fixed gap of 3/12, not a filler. The default is only used for layout: it is not written back into the source or the AST, so the AST keeps exactly what was written.
* **[2026-11-22] CI-011 Width values (planned):** The value is a whole number from 1 to 12, written without a sign, decimal point or leading zero (`width=3`, not `width=03`, `width=0`, `width=13`, `width=2.5` or `width=-1`). Widths are taken literally as N/12 of the row, so they need not add up to 12: less than 12 leaves empty space on the right of the row (a `Spacer` is the only way to move it, and only if it is not fixed by a `width`, see CI-011 Width defaults), and more than 12 makes the row overflow without wrapping, as rows already do for overflowing children. The `width` of a `Row` child is a share of the row's inner width, after its padding.
* **[2026-11-22] CI-011 Width syntax (planned):** `width` joins `link-to` in the attributes after the optional quoted text and may be combined with it in either order (`Text "Home" link-to=home width=3`), still separated by exactly one space each, each key at most once. This amends the CI-006 statement that a line has at most one attribute (there is now more than one attribute per component kind for `Box` and `Text`), and the CI-010 rule that `Spacer` cannot have any attribute: `Spacer` may now have `width` (`Spacer width=2`) but still not `link-to` or `id`. The fail-fast errors (1-based line number, like all others) are: `Page cannot have width`; `Attribute "width" requires a whole number from 1 to 12` for a missing or invalid value (`width=`, `width=0`, `width=13`, `width=abc`, `width=03`, `width=2.5`); `Duplicate attribute "width"`; and the existing `Unknown attribute`, shape and ordering rules otherwise. As in CI-006, the unsupported-kind check runs before the value check, so `Page "x" width=99` reports `Page cannot have width`.
* **[2026-11-22] CI-012 BoxRow (planned):** A new `BoxRow` component is exactly what `Row` is today: a single, non-wrapping row of children, left to right, with optional text, children and `width`, and a border. `Row` is changed to have no border: it is the same row layout (same padding, gap, widths, `Spacer` behaviour and syntax rules) but invisible, like `Text` is a `Box` without a border. This amends the CI-004 Row decision ("bordered") and extends the Component Library decision (now `Page`, `Box`, `Text`, `Row`, `BoxRow` and `Spacer`). Existing sources keep working but their `Row`s lose their border; write `BoxRow` to get the old look.
* **[2026-11-22] CI-012 BoxRow syntax (planned):** `BoxRow` is a type keyword used like `Row` (`BoxRow`, `BoxRow "Some Text"`, case-sensitive) and follows all the rules of `Row`: it takes `width` but not `link-to` or `id` (`BoxRow cannot have link-to`, following the existing `<Type> cannot have <key>` message), it can contain any node and it is a valid direct parent of a `Spacer`, which fills the remaining space of its direct parent `BoxRow` exactly as in a `Row`. This amends the CI-010 rule `Spacer must be inside a Row`: its message is now `Spacer must be inside a Row or BoxRow` and it is reported for a `Spacer` whose direct parent is neither. The unknown-type message lists the new type (`Unknown type "<name>" (expected Box or Text or Row or BoxRow or Spacer)`). A `BoxRow` is valid anywhere a `Row` is (as a child of a `Page`, `Box`, `Row` or `BoxRow`), and the width rules apply to it as a child and as a parent exactly as for `Row` (a `BoxRow` child with `width` in a `Row` or `BoxRow` takes its share, and its children are laid out in twelfths like those of a `Row`).
* **[2026-11-22] CI-012 Samples (planned):** Of the seeded wire frame samples, only the `Cancel`/`Submit` row of the Login Form (`src/features/wireframes/wire-frame-editor.ts`) and the `Cancel`/`Create` row of the `Create feature` page of the `Features list` wire frame (`src/features/wireframes/features-list.ts`) become `BoxRow`, so they keep their bordered look. All other `Row`s in the samples stay `Row` and so become borderless. The Syntax example below and the README example follow the Login Form sample.
* **[2026-11-22] CI-012 BoxRow implementation:** The `CI-012 BoxRow (planned)`, `CI-012 BoxRow syntax (planned)` and `CI-012 Samples (planned)` decisions are confirmed as implemented, unchanged. Clarifications: (1) the error messages are exactly `Line <n>: Spacer must be inside a Row or BoxRow`, `Line <n>: BoxRow cannot have link-to` and `Line <n>: BoxRow cannot have id`, and the unknown-type message is `Unknown type "<name>" (expected Box or Text or Row or BoxRow or Spacer)` (`boxrow` and `Boxrow` are unknown types). (2) Only the two sample `Row`s named in `CI-012 Samples (planned)` were changed to `BoxRow` (the `Cancel`/`Submit` row in `wire-frame-editor.ts` and the `Cancel`/`Create` row on the `Create feature` page in `features-list.ts`). The `Features list` wire frame also contains a block of text lines that displays the Login Form source (`shownSourceLines` in `features-list.ts`); it is not a `Row` node and was left as it was, so it still shows `Row` for the Cancel/Submit row (it already differed from the Login Form sample, e.g. by showing a `Spacer`), and the Login Form preview drawn on its `Feature detail` page keeps `Row`, per the iteration. (3) The README and the Syntax example, grammar and Data Dictionary in this capability were updated.
* **[2026-11-22] CI-013 Font (planned):** `Box`, `Text`, `Row` and `BoxRow` may have an optional `font` attribute (`Text "Log in" font=bold`). Its only allowed value is `bold`, which draws the node's own text in a bold weight; without the attribute the text has the normal weight. `Page` and `Spacer` cannot have `font`. The attribute applies to the text of the node it is written on only: it is not inherited by the node's children, which keep their own font.
* **[2026-11-22] CI-013 Font size (planned):** `Box`, `Text`, `Row` and `BoxRow` may have an optional `font-size` attribute (`Text "Log in" font-size=lg`) with the allowed values `sm`, `md` and `lg` (small, medium, large). `md` is the default and is today's look, so a node without `font-size` and a node with `font-size=md` look the same; `sm` is smaller and `lg` is larger. Like `font`, it applies to the node's own text only and is not inherited by children. `Page` and `Spacer` cannot have `font-size`. A node without text is unaffected, but the attributes are still valid on it.
* **[2026-11-22] CI-013 Font syntax (planned):** `font` and `font-size` join `link-to` and `width` in the attributes after the optional quoted text. They may be combined with the others in any order (`Text "Title" font=bold font-size=lg link-to=home width=6`), still separated by exactly one space each, each key at most once. This amends the CI-011 attribute list (now up to four attributes on a `Box` or `Text`, and `width`, `font` and `font-size` on a `Row` or `BoxRow`); `Spacer` still accepts only `width`. The fail-fast errors (1-based line number, like all others) are: `Page cannot have font` and `Page cannot have font-size`; `Spacer cannot have font` and `Spacer cannot have font-size` (following the existing `<Type> cannot have <key>` message); `Attribute "font" requires the value bold` for a missing or other value (`font=`, `font=italic`, `font=Bold`); `Attribute "font-size" requires one of sm, md or lg` for a missing or other value (`font-size=`, `font-size=xl`, `font-size=LG`); `Duplicate attribute "font"` and `Duplicate attribute "font-size"`. As in CI-006 and CI-011, the unsupported-kind check runs before the value check (`Page "x" font=italic` reports `Page cannot have font`).
* **[2026-11-22] CI-013 Samples (planned):** The seeded wire frame samples (`src/features/wireframes/`) are updated to show off the new attributes, using a consistent convention: page and section headings are `font=bold font-size=lg`, field labels (`Email`, `Password`) are `font=bold`, and secondary or help text is `font-size=sm`. Concretely: (1) `wire-frame-editor.ts`: `Text "Log in"` and `Text "Forgot password"` are `font=bold font-size=lg`; `Text "Email"` and `Text "Password"` are `font=bold`; `Text "Forgot password?"` becomes `Text "Forgot password?" link-to=forgot font-size=sm`; `Text "Enter your email"` is `font-size=sm`. (2) `page-links.ts`: `Text "Welcome home"` and `Text "About this product"` are `font=bold font-size=lg`. (3) `features-list.ts`: the `Features` heading, the `Create feature` title and `Feature: Wire frame editor` are `font=bold font-size=lg`; the feature description texts (the two on the `Features` page and the one on the `Feature detail` page) are `font-size=sm`; the `shownSourceLines` block mirrors the new Login Form source lines, and the Login Form preview drawn on the `Feature detail` page gets the same bold large `Log in` title. Layout, links, structure and all other nodes are unchanged. The Syntax example below and the README example follow the Login Form sample.

* **[2026-11-22] CI-015 Image (planned):** A new `Image` component is a placeholder for a picture: it is drawn as a `Box` (bordered, same look) with an X through it (two diagonal lines from corner to corner), the usual wire frame notation for an image. It has no text and no children. It may have `width` (its share of a `Row` or `BoxRow`, as for other nodes) and `link-to` (so it can be clicked like a `Box`). It may be a child of a `Page`, `Box`, `Text`, `Row` or `BoxRow`. This extends the Component Library decision (now `Page`, `Box`, `Text`, `Row`, `BoxRow`, `Spacer` and `Image`).
* **[2026-11-22] CI-015 Image syntax (planned):** In the syntax `Image` is a type keyword written alone on its line, optionally followed by attributes (`Image`, `Image width=4`, `Image link-to=home width=4`), case-sensitive like other types (`image` is an unknown type). It follows the existing attribute rules (exactly one space between tokens, any order, each key at most once). The fail-fast errors (1-based line number, like all others) are: `Image cannot have text` (`Image "x"`), `Image cannot have children` (an indented line under an `Image`, reported on the child's line), `Image cannot have font` and `Image cannot have font-size` (following the existing `<Type> cannot have <key>` message; `Image cannot have id` likewise). `Image ""` is accepted, because `""` equals omitted text. The unknown-type message lists the new type: `Unknown type "<name>" (expected Box or Text or Row or BoxRow or Spacer or Image)`.
* **[2026-11-22] CI-015 Image size (planned):** An `Image` has no content to give it a size, so in the preview it has a minimum size of 6rem wide by 6rem high (a square), and otherwise sizes like a `Box` (it stretches across a column, and takes its `width` share in a `Row` or `BoxRow`). Rows and `width` layout work as before.
* **[2026-11-22] CI-015 Image aspect ratio:** An `Image` may have an optional `aspect-ratio` attribute, written `W:H`, that fixes the shape of the picture placeholder from its width (`Image aspect-ratio=1:1` is a square, `aspect-ratio=16:9` is wide). It is chosen over a fixed height because an image's width is fluid (it stretches in a column and takes its `width` share in a row), so a fixed height would give a shape that changes with the parent, whereas a ratio keeps the shape. Each part is a whole number from 1 to 99 without sign, decimal point or leading zero (`1:1`, `16:9`, `3:4`; not `0:1`, `100:1`, `01:1`, `1.5:1` or `1`). It is valid on `Image` only, may be combined with `link-to` and `width` in any order (each key at most once, one space between tokens) and is the only attribute of this kind. The default is `1:1`: an `Image` without `aspect-ratio` is a square, exactly as if `aspect-ratio=1:1` were written. This amends `CI-015 Image size (planned)`: the 6rem minimum height is replaced by the ratio, so the height always follows from the width and the ratio always holds, while the 6rem minimum width remains (an `Image` is therefore at least 6rem square by default, and `aspect-ratio=16:9` is at least 6rem by 3.375rem). Note that a default `Image` stretching across a column is as tall as it is wide. In a `Row` or `BoxRow` an `Image` keeps its own height instead of stretching to the tallest sibling (the siblings still stretch to it). The fail-fast errors (1-based line number, like all others) are: `Attribute "aspect-ratio" requires a ratio such as 16:9 (whole numbers from 1 to 99)` for a missing or invalid value, `Duplicate attribute "aspect-ratio"`, and `<Type> cannot have aspect-ratio` for any type other than `Image` (e.g. `Box cannot have aspect-ratio`; checked before the value, as for the other attributes). It is not a `width` or `height`: it changes no other node and has no effect outside an `Image`.

## Technical Decisions
* **[2026-11-20] Base Schema:** The AST will use a node-based tree structure. 
* **[2026-11-20] CI-001 Tooling:** Implemented in `src/schema/ast.ts` with Zod 4 (`zod`), TypeScript, and Vitest for tests, managed with pnpm. Types are derived via `z.infer` so schema and types cannot drift.
* **[2026-11-20] CI-001 Strictness:** Nodes use `z.strictObject` (unknown keys rejected). `id` is a non-empty string; `type` is `z.enum(["Box", "Text"])`; `text` and `children` are required (`text` may be `""`, leaf nodes use `children: []`) so payloads are deterministic with no implicit defaults.
* **[2026-11-20] CI-001 Recursion:** The recursive `children` field uses Zod 4's getter syntax rather than `z.lazy`, preserving type inference.
* **[2026-11-20] CI-001 Unique IDs:** `AstSchema` (the root schema) additionally enforces `id` uniqueness across the whole tree via `superRefine`; `AstNodeSchema` validates a single subtree without that check.
* **[2026-11-20] CI-001 Border representation:** No `border` field is added; the border difference between `Box` and `Text` is derived from `type` by renderers, since the Data Dictionary doesn't include it.
* **[2026-11-20] CI-001 Login Form fixture:** With only `Box` and `Text` available, inputs and buttons are modelled as `Box` nodes (label as `Text`, placeholder/button caption in `text`).
* **[2026-11-20] CI-003 Schema:** Removed `id` from `AstNodeSchema` (now `type`, `text`, `children`; still `z.strictObject`, so a stray `id` is rejected) and removed the duplicate-id `superRefine`. `AstSchema` is now simply an alias of the root node schema and is still exported, along with `Ast`/`AstNode`.
* **[2026-11-20] CI-003 Parser:** `parseSyntax(source)` in `src/syntax/parse.ts` is a hand-written, line-based parser (no parser-generator dependency). It returns `ParseResult` (`{ ok: true; ast } | { ok: false; error }`, moved here from the removed `src/viewer/parse.ts`). It splits on `\r?\n`, ignores whitespace-only lines, and keeps a stack of the latest node per indentation level to attach children. ## Syntax

```
Page "Log in" id=login
  Box
    Text "Log in" font=bold font-size=lg
    Box
      Text "Email" font=bold
      Box "you@example.com"
    Box
      Text "Password" font=bold
      Box "*********"
    Text "Forgot password?" link-to=forgot font-size=sm
    BoxRow
      Box "Cancel" width=3
      Spacer width=6
      Box "Submit" width=3
Page "Forgot password" id=forgot
  Text "Enter your email"
  Box "you@example.com"
  Text "Back to log in" link-to=login
```

Grammar (informal): `source = page*`, `page = "Page" " " quoted [" id=" name] NL node*` (the title is mandatory) with the nodes indented one level, `line = indent Type [" " quoted] (" " attribute)*` with `attribute = "link-to=" name | "width=" width | "font=bold" | "font-size=" size` (`link-to` only for `Box`, `Text` and `Image`, `width` for `Box`, `Text`, `Row`, `BoxRow`, `Spacer` and `Image`, `font` and `font-size` for `Box`, `Text`, `Row` and `BoxRow`; the attributes may be written in any order, each at most once), `indent = "  "*`, `Type = "Box" | "Text" | "Row" | "BoxRow" | "Spacer" | "Image"` (inside a page; a `Spacer` is written alone, `line = indent "Spacer" [" width=" width]`, only as a direct child of a `Row` or `BoxRow`, with no text, `link-to` or children; an `Image` is written alone, `line = indent "Image" (" " attribute)*` with only `link-to`, `width` and `aspect-ratio`, and has no text, `font`, `font-size` or children), `attribute` also includes `"aspect-ratio=" ratio` (only for `Image`, default `1:1`), `ratio = part ":" part`, `part = "1" | "2" | ... | "99"` (no sign, decimal point or leading zero), `quoted = '"' [^"]* '"'`, `name = [A-Za-z0-9_-]+`, `size = "sm" | "md" | "lg"`, `width = "1" | "2" | ... | "12"` (no sign, decimal point or leading zero; the unit is twelfths of the parent `Row`, ignored outside a `Row`). `Page` is only valid at indent 0, and every indent-0 line must be a `Page`. Page ids must be unique; a `link-to` may name any id (unknown targets are not a syntax error).

## Data Dictionary
- `pages`: The root of the AST - a non-empty array of pages.
- `Page.title`: The page's title, mandatory in the syntax (the written string may be `""`), used by the viewer as the tab label.
- `Page.id`: Optional identifier of the page (`[A-Za-z0-9_-]+`, unique across pages), the target of links. Omitted when the page has no `id=`.
- `Page.children`: Array of the page's top-level AST nodes (`Row`, `BoxRow`, `Box`, `Text` or `Image`).
- `linkTo`: Optional on a node (written `link-to=` in the syntax, only for `Box`, `Text` and `Image`): the `id` of the page to open when the node is clicked in the viewer. Omitted when the node has no link.
- `width`: Optional on a node (written `width=` in the syntax, for `Box`, `Text`, `Row`, `BoxRow`, `Spacer` and `Image`): its width in twelfths of its parent `Row` or `BoxRow`, a whole number from 1 to 12. Omitted when not written (the viewer treats a missing width as 3 in a `Row` or `BoxRow` where a sibling has one); no effect outside a `Row` or `BoxRow`. A `Page` has no `width`.
- `aspectRatio`: Optional on a node, `Image` only (written `aspect-ratio=` in the syntax): the shape of the image as a string `W:H`, each part a whole number from 1 to 99 (e.g. `"16:9"`). Omitted when not written (the viewer treats a missing `aspectRatio` as `1:1`); `1:1` written explicitly is kept. Any other node type with an `aspectRatio` is rejected.
- `font`: Optional on a node (written `font=bold` in the syntax, for `Box`, `Text`, `Row` and `BoxRow`): `"bold"`, the only allowed value, draws the node's own text in bold. Omitted when not written (normal weight). Not inherited by children. A `Page` or `Spacer` has no `font`.
- `fontSize`: Optional on a node (written `font-size=` in the syntax, for `Box`, `Text`, `Row` and `BoxRow`): `"sm"`, `"md"` or `"lg"`, the size of the node's own text. Omitted when not written (the viewer treats a missing `fontSize` as `md`); `md` written explicitly is kept. Not inherited by children. A `Page` or `Spacer` has no `fontSize`.
- `type`: The component primitive of a node - `Box`, `Text`, `Row`, `BoxRow`, `Spacer` or `Image`. `Image` is a picture placeholder drawn as a `Box` with an X through it, with `text: ""`, `children: []`, no `font` and no `fontSize` (it may have `linkTo`, `width` and `aspectRatio`). `Row` lays its children out on a single row and has no border; `BoxRow` is a `Row` with a border. `Spacer` is invisible, fills the remaining space of its parent `Row` or `BoxRow` and is only valid as a direct child of one of them, with `text: ""`, `children: []` and no `linkTo`. `Page` is not a node type.
- `text`: The text content of the node - for both `Box` and `Text` nodes.
- `children`: Array of nested AST nodes.
