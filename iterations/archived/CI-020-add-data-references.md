# Iteration CI-020: Add Data References

**Target Capability:** `/capabilities/data-references/capability.md`

## User Story
As a Trellis author, I want to write `@User.FirstName.label` or `@User.FirstName` as the text of a node, and pass `@User.FirstName` to a macro, so that the wire frame shows the label and sample value from the data dictionary instead of text I retype. Read the whole capability first (all `CI-020` decisions, Syntax and Data Dictionary), then `/capabilities/macros/capability.md` (`CI-017` and `CI-019` argument and substitution rules) and `/capabilities/data-dictionary/capability.md`.

## Acceptance Criteria
1. `src/web/schema/ast.ts` exports `PointerRefSchema` and `AstNodeSchema` has the optional `ref` key as decided; a `ref` on a `Page`, `Spacer` or `Image` is rejected. Tests are added to `ast.test.ts`.
2. `parseSyntax` accepts an unquoted pointer as the text of a `Box`, `Text`, `Row` or `BoxRow` (with or without attributes after it) and produces a node with `text: ""` and a `ref` (`kind` `mock` when no suffix, otherwise the written `entity`, `field`, `dataType`, `label` or `mock`, `line` set). It reports the exact `Invalid pointer ...` and `Pointer "<token>" must name a field ...` errors, other bare text is still an error, `"@User.FirstName"` in quotes is plain text, and a pointer on `Page`, `Spacer` or `Image` is an error. Tests are added to `parse.test.ts`.
3. `src/web/syntax/resolve.ts` exports `resolveReferences(ast, rows)`: a pointer of each kind (`entity`, `field`, `dataType`, `label`, `mock`) is replaced by the matching column of the row (`mock` is `mockValue`; empty values give empty text), the first row wins for a duplicate entity and field, `Unknown entity "<Entity>"` and `Unknown field "<Entity>.<Field>"` are reported fail-fast with `Line <n>: `, and an AST without pointers comes back unchanged. Tests are in `resolve.test.ts`.
4. `compileSyntax(source, sharedMacros?, dataDictionary?)` resolves pointers after parsing and maps a resolver error line back to the line of the source as written, with ` (in macro "<Name>")` when the pointer came from a macro body. A source with no pointer gives the same result as before. Tests are added to `compile.test.ts`.
5. A bare macro argument that starts with `@` is a pointer and a quoted one is a literal. For a plain parameter the pointer is substituted as the value. For an object parameter `field=@User.FirstName` fills every declared field named after a column (`entity`, `field`, `dataType`, `label`, `mockValue`) as in `CI-020 Pointer arguments for macros (planned)` and `CI-020 Any column (planned)` (a declared field that is not a column name, an entity pointer or an invalid pointer gives the exact error in the capability), and the piped form is unchanged. A placeholder that is the whole content of a quoted string and is replaced by a pointer drops the quotes; any other placeholder is replaced as before. The example in the capability (`Def Field $field=label|mockValue`, `Field field=@User.FirstName`) expands and resolves as described. Tests are added to `macros.test.ts` and `compile.test.ts`, including that all existing macro tests still pass.
6. `WireframeEditor` and `MacroEditor` take the optional `dataDictionary` prop and compile with it. The feature details page waits for the data dictionary (as well as the feature and the macros) before showing the editor, and the Macros page loads the data dictionary and waits for it. Editing the data dictionary on the feature details page updates the preview. Tests (`renderToStaticMarkup`) are added or updated in `wireframe-editor.test.tsx`, `macro-editor.test.tsx` and `src/web/pages/features.test.tsx`; typing is not DOM-tested.
7. The seeded wire frames, the seeded global macros and the data dictionary table are unchanged.
8. `pnpm test` passes, `pnpm build` succeeds and `pnpm lint` is clean.
9. `README.md` is updated with a short note on data references in its feature overview (no implementation detail), and every decision made while implementing is logged in `/capabilities/data-references/capability.md` under Product Decisions or Technical Decisions, confirming or amending the `(planned)` entries.
