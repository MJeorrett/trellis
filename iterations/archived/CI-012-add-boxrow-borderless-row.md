# Iteration CI-012: Add BoxRow, Borderless Row

**Target Capability:** `/capabilities/trellis-ast/capability.md`

## User Story
As a Trellis user or AI agent, I want `Row` to have no border and a new `BoxRow` that is exactly today's bordered `Row`, so that I can lay items out on a row without a box around them, and still draw a bordered row when I want one.

Read the `CI-012` entries in the Product and Technical Decisions of the target capability, and the `CI-012 BoxRow (planned)` entries in `/capabilities/wire-frame-viewer/capability.md`, before starting. They define the `BoxRow` syntax and rules (same as `Row`: `width` yes, `link-to` and `id` no, valid parent of a `Spacer`), the new `Spacer` error message, which samples change, and how the viewer derives "is a row" and "has a border".

## Acceptance Criteria
1. `src/schema/ast.ts`: `NodeTypeSchema` is `z.enum(["Box", "Text", "Row", "BoxRow", "Spacer"])` and `checkSpacers` accepts a `Row` or `BoxRow` parent, reporting `Spacer must be inside a Row or BoxRow` otherwise. `src/schema/ast.test.ts` covers `BoxRow` as a valid node (with text, children and `width`), nested in a `Page`, `Box`, `Row` and `BoxRow`, and a `Spacer` valid directly in a `BoxRow` and rejected elsewhere with the new message.
2. `parseSyntax` in `src/syntax/parse.ts` accepts `BoxRow` like `Row` (`BoxRow`, `BoxRow "Some Text"`, with `width=N`, nested, with children and a `Spacer`) and produces `type: "BoxRow"`. `BoxRow link-to=x` reports `Line <n>: BoxRow cannot have link-to` and `BoxRow id=x` reports `Line <n>: BoxRow cannot have id`. `boxrow` and `Boxrow` are unknown types (case-sensitive). The unknown-type message is `Unknown type "<name>" (expected Box or Text or Row or BoxRow or Spacer)` and the `Spacer` parent error is `Line <n>: Spacer must be inside a Row or BoxRow`. A `Spacer` under a `BoxRow` is accepted.
3. `src/syntax/parse.test.ts` covers every case in criterion 2 with full ASTs and exact error messages, and the existing tests that mention the unknown-type or `Spacer` parent messages are updated. The sample parse tests expect the converted samples (criterion 6).
4. `WireframeNode` in `src/viewer/wireframe.tsx` treats `Row` and `BoxRow` as rows (`flex-row flex-nowrap`, children laid out with `rowWidths`) and gives a border and wobbly corners to every type except `Text` and `Row`. A `Row` is therefore borderless, with no `borderRadius`, but keeps the font, tilt, padding, gap, widths and `Spacer` behaviour. A `BoxRow` renders exactly as a `Row` did before this iteration. `data-node-type` is `Row` or `BoxRow`. The doc comment on `WireframeNode` is updated.
5. `src/viewer/wireframe.test.tsx` (with `renderToStaticMarkup`) verifies: `Row` has `flex-row flex-nowrap`, no `border` class and no `border-radius`; `BoxRow` has `flex-row flex-nowrap`, the border and the `border-radius`, and `data-node-type="BoxRow"`; the `width` layout and the `Spacer` (`flex-1` without widths, fixed with widths) work in a `BoxRow` as in a `Row`; the existing `Row` tests are updated for the missing border. `src/viewer/layout.test.ts` is unchanged unless `rowWidths` needs it.
6. Samples: the `Cancel`/`Submit` `Row` in `src/features/wireframes/wire-frame-editor.ts` and the `Cancel`/`Create` `Row` on the `Create feature` page in `src/features/wireframes/features-list.ts` become `BoxRow`. All other `Row`s in the samples stay `Row`. The `Syntax` example in the target capability and the README example follow the Login Form sample.
7. `pnpm test` passes and `pnpm build` succeeds.
8. Updates `README.md` (the syntax section: `BoxRow` and its rules, `Row` now borderless, the `Spacer` error message, the attribute lists and the page children list) and the Syntax (grammar and example) and Data Dictionary (`type`, `Page.children`) sections of the target capability, and logs the implementation decisions in the target capability's Product Decisions or Technical Decisions (and a note in `/capabilities/wire-frame-viewer/capability.md` if the rendering differs from the plan).
