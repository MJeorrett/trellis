# Iteration CI-016: Add Data Dictionary Pane

**Target Capability:** `/capabilities/data-dictionary/capability.md`

## User Story
As a Trellis user, I want a data dictionary pane at the bottom of the feature details page, spanning the full width below the code and the wire frame preview, where I can list entities, fields and data types, so that I can describe the data my product works with next to its wire frames. The details page fills the window without a page scroll bar: the data dictionary shows 5 rows and scrolls beyond that, and the wire frame source and preview share the remaining height and scroll inside their cards when needed.

Read the `CI-016` entries in the Product Decisions, Technical Decisions and Data Dictionary of the target capability before starting, and the `CI-016 Data dictionary pane on the details page (planned)`, `CI-016 Static details layout (planned)` and `CI-016 Static layout (planned)` entries in `/capabilities/features/capability.md`. They define the columns, the Pascal case rule, the editing, the fixed-height pane, the static layout, the global storage, the schema, the API and the component.

## Acceptance Criteria
1. `src/web/data-dictionary/schema.ts` exports `DATA_TYPES` (`int`, `bool`, `datetime`, `string`, in that order), `DataTypeSchema`, `DataDictionaryRowSchema` (a `z.strictObject` of `entity`, `field` and `dataType`), `PASCAL_CASE_PATTERN` and the derived types `DataType` and `DataDictionaryRow`, as in `CI-016 Schema (planned)`.
2. `src/web/data-dictionary/logic.ts` exports pure, DOM-free `validateRowField`, `newRow`, `updateRow` and `removeRow`. `validateRowField` gives `Entity is required` / `Field is required` for a blank value, `Entity must be Pascal case` / `Field must be Pascal case` for a value that does not match `PASCAL_CASE_PATTERN`, and `undefined` for a valid one. `newRow()` gives an empty entity, an empty field and `string`. `updateRow` and `removeRow` return new arrays and leave their input unchanged.
3. `src/web/data-dictionary/api.ts` exports `getDataDictionary`, `saveDataDictionary`, `resetMockDataDictionary`, `setMockDelay` and `DATA_DICTIONARY_STORAGE_KEY` (`trellis.data-dictionary`). The rows are kept in local storage, are shared by all features, start empty (no seed), are validated with `z.array(DataDictionaryRowSchema)` on save (an invalid list rejects with an `Error` and writes nothing) and a missing or invalid stored value reads as an empty list. The API works without persistence when `localStorage` is unavailable.
4. `src/web/data-dictionary/data-dictionary-pane.tsx` exports `DataDictionaryPane` (props `rows` and `onRowsChange`), showing a `Data dictionary` heading and a table with the column headers `Entity`, `Field` and `DataType`, one row per entry in order. Each row has an `Entity` text input, a `Field` text input, a `DataType` select offering exactly `int`, `bool`, `datetime` and `string` in that order, and a delete button, with the `aria-label`s `Row N entity`, `Row N field`, `Row N data type` and `Delete row N`. An `Add field` button under the table is always shown. With no rows the table shows `No fields yet`. The pane has a fixed height of the heading, the column header row, room for exactly 5 data rows (`VISIBLE_ROWS = 5` and `ROW_HEIGHT`, exported) and the `Add field` button; it does not change height with the number of rows. Only the rows scroll vertically (more than 5 rows scroll; the heading, sticky column headers and `Add field` stay visible), and the pane accepts a `className`.
5. Editing: `Add field` calls `onRowsChange` with a new row (empty entity, empty field, `string`) appended; typing in a text input, picking a type and the delete button each call `onRowsChange` with the updated list. Typed values are never converted or trimmed. An invalid or blank `Entity` or `Field` shows its inline message under the cell (see `CI-016 Pascal case (planned)`) and marks the input `aria-invalid`; a valid value shows no message.
6. Static layout (`src/web/App.tsx`, `src/web/pages/feature-details.tsx`, `src/web/viewer/wireframe-editor.tsx`): the details page fills the window below the top nav and never shows a page scroll bar. The header block (back link, `Feature: <name>`, description) and the `Wireframe` heading are at their natural height at the top, the data dictionary pane is at the bottom at its fixed 5-row height, and the wire frame source and wire frame cards take all the height in between, side by side (stacked, sharing the height equally, on narrow windows). Each card keeps its title visible and scrolls its own content vertically when it is taller than the card (the page panes and `+ Add Page` in the source card; the page tabs and preview in the wire frame card). On a very short window the cards shrink rather than the page scrolling. The features list page still scrolls as before and `FeatureNotFound` is unchanged. `WireframeEditor`'s props, state and behaviour are unchanged.
7. `src/web/pages/feature-details.tsx`: the details page loads the data dictionary once on mount with `getDataDictionary()`, shows the pane below the `Wireframe` cards, spanning the full width of the page, updates its state immediately on every change and calls `saveDataDictionary` without waiting (a rejection is ignored). The pane shows nothing until the rows have loaded. Every feature's details page shows the same rows, and they are still there after navigating away and back and after a reload. `FeatureNotFound` shows no data dictionary. The heading, the description, the wire frame cards and their behaviour are unchanged.
8. Tests (`pnpm test`, DOM-free as before): `schema.test.ts` (each data type accepted, an unknown type and an extra key rejected, the Pascal case pattern for valid and invalid examples such as `Customer`, `OrderLine2`, `customer`, `order_line`, `Order Line`, `2Order` and `""`), `logic.test.ts` (the validation messages, `newRow`, `updateRow` and `removeRow` including that the input array is not mutated) and `api.test.ts` (starts empty, saving persists and a later read returns it, saving an invalid list rejects and writes nothing, invalid stored data reads as empty, shared across calls, the no-`localStorage` fallback, with `localStorage` stubbed like in `src/web/features/api.test.ts`). `renderToStaticMarkup` tests of `DataDictionaryPane` check the headings and columns, one row per entry with its values and the select's four options in order, `No fields yet` with no rows, `Add field` always present, the inline messages and `aria-invalid` only for invalid cells, and the pane's fixed height and scroll area (derived from `VISIBLE_ROWS` and `ROW_HEIGHT`, the same for 0, 3 and 8 rows). A `FeatureDetailsView`-level check confirms the pane appears below the wire frame (its markup comes after the `Wireframe` heading), that `FeatureNotFound` does not contain it, if the view takes the rows as props, and that the layout classes of `CI-016 Static layout (planned)` are present (`h-full min-h-0` main, the flexible editor wrapper, the fixed pane, the scrolling card content) in the details view, the editor and `App`.
9. `pnpm test`, `pnpm typecheck` and `pnpm build` pass.
10.
